# 积分经济 C4 规范

> 本文是积分商品、免费惊喜、积分抽奖、消费协议与运营观测的单一产品规范。代码中的权威目录位于 `apps/server/util/pointsEconomyCatalog.js`；任何价格、概率、等级或奖池变化都必须升级经济版本并同步测试、本文与帮助中心。

积分获取、用户积分中心、Root 治理、余额对账与活动发放由独立的 [积分获取与治理 C5 规范](./points-earning-c5.md) 管理。C4 的 `economyVersion` 与 C5 的 `policyVersion` 不得混用：商品或抽奖请求继续提交 `points-economy-c4`，任务和成就流水记录实际获取策略版本。

## 目标与边界

- C4 定价锚点按稳定理论周上限 670 设计；C5 可以在签到、每日任务和每周挑战之间重分配，但不能在不升级获取策略版本和重新评审购买周期的情况下改变该总上限。
- AI 永久余额、永久空间和头像框按不同使用价值定价，避免只提高某一类商品导致相对价值失真。
- 每日惊喜是轻量等级权益，不承担永久空间或补签卡发放，也不推进积分抽奖保底。
- 积分抽奖是自愿的娱乐性积分出口；用户明确需要 AI 或空间时，直接兑换必须更稳定、更划算。
- 已有积分、永久余额、永久空间和已拥有头像框不回收、不贬损；旧抽奖可见保底进度只继承一次。

## 版本与消费幂等

商店购买、每日惊喜和积分抽奖都必须提交：

- `clientRequestId`：12～64 位 `[A-Za-z0-9:_-]`，相同规范负载在结果未知时复用；
- `economyVersion`：来自商店或抽奖状态响应，不允许前端写死；
- `expectedCost`：用户确认时看到的价格，免费操作为 0。

服务端先按 `(user_id, request_id)` 读取 `points_economy_operations` 收据，再校验当前版本和价格。相同请求回放原结果并返回 `idempotent: true`；同一请求号换负载返回 `IDEMPOTENCY_KEY_REUSED`；旧页面或价格变化返回 409 应用信封，且不得扣分、发资产、占免费次数或推进保底。

前端只在网络超时、离线、连接重置或服务端明确仍处理中时保留请求号；已知成功或已知业务失败后清理。待请求按账号、操作和跨版本稳定的业务语义分别定位（商品 ID，或抽奖模式 + 次数），并把完整原始负载一并保存，不能让十连覆盖单抽或让不同商品互相覆盖。状态接口观察到目录版本变化时也不能清理或改写结果未知的旧请求；它必须连同原版本和原价格重放，供服务端先跨版本恢复旧收据。

结果未知的请求不设置客户端时间过期；`sessionStorage` 会随标签页会话结束而回收，而当前会话内必须一直复用原请求号，直到拿到确定结果。

## Schema、迁移与激活顺序

1. 上线兼容代码，但保持 `POINTS_ECONOMY_C4_ENABLED=false`。
2. 暂停商店、每日惊喜和积分抽奖写入口。
3. 执行 `20260813_points_economy_c4.sql`：创建收据/迁移状态表、补付费字段，并只执行一次旧进度继承。
4. 运行只读 Schema 门禁，核对迁移标记、收据聚合索引与抽奖聚合；回填不改变积分余额或任何资产。
5. 同批执行 `20260813_points_economy_c4_knowledge.sql`，刷新帮助中心。
6. 前后端同批发布后开启 C4，再按“每日惊喜 → 积分抽奖 → 商店”逐项放开。

C4 激活时应用启动会检查 `points-economy-c4-paid-pity-v1` 标记；缺失则失败关闭，禁止在启动 `ensure*()` 中静默回填历史业务数据。

### 运行时开关

- `POINTS_ECONOMY_C4_ENABLED`
- `POINTS_ECONOMY_REQUIRE_WRITE_VERSION`
- `POINTS_SHOP_PURCHASE_ENABLED`
- `POINTS_LOTTERY_FREE_ENABLED`
- `POINTS_LOTTERY_PAID_ENABLED`

开关只接受明确的 true/false/1/0，未知值按关闭解析。兼容代码回滚使用 C3 目录；资产与新流水不反向删除，已成功的 C4 请求即使跨版本重试也必须回放原收据。

## 流水与运营观测

新 reason：`lottery_paid_cost`、`lottery_paid_win`、`lottery_paid_asset`、`lottery_paid_compensation`、`lottery_free`、`lottery_free_win`、`lottery_free_asset`；历史 `lottery_cost`、`lottery_win`、`lottery_storage`、`lottery_compensation` 必须继续可查。

上线前可运行 `node apps/server/scripts/auditPointsEconomy.js` 做只读基线审计。上线后按日观察：

- 稳定/一次性积分发行、商店消费、付费抽成本与积分返还、每日惊喜积分发行；
- 免费/付费 AI 发放、付费永久空间发放、直接购买永久空间；
- 商品兑换数、余额分布、净发行、免费与付费抽次数、保底命中、幂等回放；
- AI 余额真实消耗与扩容后的空间使用率。

调参只升级目录版本，不原地修改 C4 快照。观察到免费池重新成为主要积分发行源时，优先调免费次数或概率；AI/空间需求不足时结合真实消耗判断，不用单一兑换量直接推导价格。

## 验收底线

- 目录快照、权重合计、免费次数阶梯、总价与等级门槛有自动测试。
- AI、空间、头像框购买覆盖余额不足、等级不足、版本冲突、响应丢失重放和并发同请求。
- 免费抽永远不出现存储/补签卡且不改变付费保底；付费第 10 抽、十连跨保底和满卡补偿均原子提交。
- 商店和头像框抽屉读取同一服务端目录；抽奖页同时可查看两池，加载失败时禁用操作而不是回落旧价格。
- Agent、管理员统计、用户积分明细和帮助中心同时理解新旧 reason 与 C4 规则。
- 不为本次经济调整新增全局 CSS、页面级监听、轮询或逐条额外请求。
