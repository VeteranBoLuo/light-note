# 积分获取与治理

> 本文是积分获取策略、用户积分明细与兑换目标、Root 积分治理、对账与活动发放的单一产品规范。商品价格、兑换上限、每日惊喜和付费抽奖以 [积分经济](./points-economy.md) 为准；获取策略版本不改变消费协议。

> C8 收紧每日、每周和未来成就的积分，任务条件沿用 C6/C7。历史周期仍按其固化版本解释；每日任务组合见 [C6 每日任务](#c6-每日任务)，奖励和切换见 [C8 获取预算](#c8-获取预算)。

## 目标与边界

- 本文管理积分获取、解释与治理；消费规则由积分经济文档管理。
- C8 稳定理论周上限为 365；C5/C6 历史上限 670，社区周规则 C7 为 690。签到、经验、免费惊喜和连签里程碑积分保持原规则。知识庄园等新增奖励来源须纳入获取预算后另行定版，不能在既有任务收入上无限叠加。
- 积分规则服务于书签、笔记、文件、待办和整理等知识管理行为，不设计页面浏览、反复点击或领取奖励式任务。
- 已有余额、资产、领取事实和旧周奖励永久保留；已解锁未领取的旧成就固化旧奖励快照。
- Root 治理首先提供可解释、可审计的事实。暂不为高级指标建立复杂数仓，也不因一次异常自动封号或自动覆盖余额。

## 版本与数值

获取策略的 `policyVersion` 与消费目录的 `economyVersion` 独立。获取规则由 `apps/server/util/pointsEarningPolicy.js` 定义，组件、路由、Agent 和帮助中心不得复制奖励常量。

### 稳定可重复收入

以下为历史 C5/C6 周期规则；C7 只扩展社区周任务。C8 数值见下节。

| 来源     | C5 规则                                       | 理论周上限 |
| -------- | --------------------------------------------- | ---------: |
| 签到     | 首日 15，连续第 2～6 日为 16～20，此后保持 20 |        140 |
| 每日任务 | 完成 2/3 得 15；完成 3/3 再得 25              |        280 |
| 每周挑战 | 5 项合计 250                                  |        250 |
| 合计     | 不含成就、每日惊喜和运营发放                  |    **670** |

仅 C5 生效周期的每日三项任务固定为：今日签到、完成 1 个知识行动、再完成 1 个独立知识事件。允许同模块中的两个不同资源事件，不允许一个事件同时完成后两项。

每周挑战固定为：收藏 5 次（40）、笔记 3 次（60）、完成待办或整理 5 次（60）、有效活跃 5 天（50）、完成 3 类知识管理操作（40）。最后一项指在新增书签、新建笔记、上传文件、完成待办、整理资源中任选 3 类；同一类型无论完成多少次，在该挑战内都只计为 1 类。同一个真实事件可以为不同统计维度提供事实，但同一挑战内不能重复计数。

### 社区周任务与成就

社区参与不进入每日任务池。C7 仅扩展每周目录：保留 C5 五项，再增加「本周分享」，本周首次审核通过 1 篇帖子可领 20 积分。周任务合计 270，稳定理论周上限为 690；C5/C6 历史口径保持 670。同一篇活动帖子可同时满足周任务与对应活动条件，领取仍各自幂等。

帖子以 `community_posts.published_at` 的首次发布时间为事实，按账号时区归入审核通过的 ISO 周。待审核、被拒绝的帖子不计数；修改、再次审核、撤回及恢复均不重置首次时间。社区成就累计不同的首次公开帖子；回答成就只在求助作者采用其他人的回答时记录 `community_accepted_answers`，同一回答反复采用不累计。已达成成就永久保留。

成就目录、阈值和奖励由 `growth.js` 定义，前端复用成就墙、统一领取与社区精选徽章。发表和采用事务只写事实及幂等 outbox，Worker 可重试地固化成就快照，成长看板只读派生进度，领取事务固化尚未入表的解锁状态；不在正文中保存成长元数据。

C7 需显式配置 `POINTS_EARNING_C7_EFFECTIVE_WEEK=YYYYWW`，在新的完整 ISO 周启用 `POINTS_EARNING_C7_ENABLED=true`，且依赖 C5 启用与社区 Schema 就绪。沿用日规则版本，不改每日任务。已有周期锁优先；暂停 C7 写闸不会退回旧周目录，已领取记录保持有效。部署前执行社区显式迁移并验证 Worker；不要在周中切换目录。

### 来源分类

- 稳定：`checkin`、`quest`、`weekly`。
- 一次性：`achievement`、`streak_milestone`。
- 随机：免费/付费惊喜中奖及历史抽奖兼容 reason。
- 运营：`admin`、`campaign`、`correction`。
- 消费：所有负向 `delta`，按实际 reason 保留明细。

随机回流不能显示成“保证可得”，不计入稳定理论周上限。每日惊喜的次数、奖池与期望由 [积分经济](./points-economy.md#每日惊喜) 统一维护。

## C6 每日任务

每天固定保留 3 个槽位：

1. 完成每日签到；
2. 从可立即完成的任务池随机选择 1 项；
3. 再从同一任务池选择 1 项，且不得与上一项重复。

任务池只保留无需预先拥有内容、进入对应页面即可开始的动作：收藏书签、新建笔记、上传文件、创建待办。完成待办和整理资源需要用户先有可完成的待办或待整理资源，因此不作为无条件每日任务，仍可参与现有每周统计。每日不再出现“完成 1 个知识行动 / 再完成 1 个知识行动”或“新增任意内容 + 具体创建任务”等语义重叠。每项任务目标均为 1 个独立事实；奖励仍为完成 2/3 得 15 积分和 5 经验，完成 3/3 再得 25 积分和 10 经验。

任务与事实对应关系：

| 任务 key            | 文案         | `growth_events` 行为类型 |
| ------------------- | ------------ | ------------------------ |
| `daily_bookmark`    | 收藏一条书签 | `bookmark`               |
| `daily_note`        | 写一篇笔记   | `note`                   |
| `daily_file`        | 上传一个文件 | `file`                   |
| `daily_todo_create` | 创建一个待办 | `todo_create`            |

### 稳定随机规则

- 选择只在服务端完成，输入为账号 ID、账号时区自然日和固定 C6 目录。
- 同一账号同一天在刷新、重启、PC、移动浏览器和 App 中必须得到同一组合。
- 4 个任务两两组合构成 6 种组合；先按账号稳定洗牌，再按自然日轮换。周期内组合不重复，相邻两天不会出现完全相同的组合。
- C6 目录在版本内不可修改。新增任务、移动任务分组或改变完成条件必须升级获取策略版本，不能原地改变当天可重算结果。
- 当前目录完全由版本化输入确定，因此不新增可漂移的每日分配副本，也不让成长看板 GET 产生写入；日策略版本继续由 `points_earning_period_policy` 在领取事务中固化。

### 完成与防重

- 完成状态只读取账号时区当天的低敏感、不可变 `growth_events`，不回查业务表拼接第二套口径。
- 每个随机任务只读取自己的行为类型；两个槽位类型互斥，因此同一事件不能完成两项每日任务。
- 同一事件仍可按现有规则参与不同维度的每周统计，但不能在每日任务内部重复占槽。
- 游客、新手示例、管理员预览、`suppressUserRewards`、系统回填、页面浏览、领取和抽奖继续排除。
- 领取事务重新计算任务状态，使用 `daily:c6:<YYYYMMDD>:<2|3>` 幂等 ref；客户端状态不能作为发奖依据。

### 激活与回滚

- C6 依赖已经完成并启用的 C5 账本、迁移标记和日/周边界。
- 配置 `POINTS_EARNING_C6_EFFECTIVE_DAY=YYYYMMDD`，且不得早于 C5 生效日；到达完整账号自然日后，日策略选择为 `points-earning-c6`。
- `POINTS_EARNING_C6_ENABLED` 是 C6 发放写闸，不参与已经生效日期的版本回退；C5 总闸关闭时 C6 同样暂停。
- 回滚只关闭 C6 写闸。已经进入 C6 的自然日继续显示 C6 任务并暂停发奖，禁止回落 C5 形成同日双领。

### 每日任务验收

1. 同账号同日跨端和重复刷新任务完全一致；连续 6 天组合不重复，相邻两天不会出现完全相同的组合。
2. 每日始终为签到和两个不同的可立即完成任务，没有通用知识行动槽，也不要求用户预先拥有待办或待整理资源。
3. 只产生第一项随机任务的事实时完成度为 2/3，不得同时完成另一项。
4. C5 生效日仍使用 `daily:c5`，C6 生效日使用 `daily:c6`；暂停 C6 写闸不回退任务版本。
5. 奖励总额、每周挑战、成就和稳定理论周上限与 C5 一致。

## C8 获取预算

C8 保留每日三项任务与两阶段领取：完成 2 项得 5 积分和 5 EXP，完成 3 项再得 10 积分和 10 EXP，每天任务合计 15 积分。具体任务仍按固定 C6 输入选择，升级只调整奖励，不重抽任务。

每周六项条件沿用 C7，积分依次为收藏 20、笔记 25、推进待办或整理 25、有效活跃 20、知识管理操作种类 20、社区分享 10，合计 120。签到最高每周 140，因此稳定理论周上限为 `140 + 15 × 7 + 120 = 365`；不把随机惊喜计为保证收入。日规则和周规则跨边界先后生效时，积分中心分别读取各自固化版本计算额度。

未来解锁成就的积分按 C5/C7 目录减半，条件和头像框保持不变；已领取事实、余额及已解锁奖励快照完整保留。成就没有周期：维护窗口内完成旧承诺快照后，配置 C8 并恢复服务即采用新成就目录，每日和每周任务仍等待各自完整边界。成就卡片、单项与批量领取均使用同一奖励快照，不用新目录覆盖旧承诺。

### C8 准备与激活

- 在维护窗口停止 API 与相关 Worker 写入，保持 C8 未配置。执行 `node apps/server/scripts/preparePointsEarningC8.js` 只读预览，获授权后加 `--apply` 固化所有已达成成就。工具复用成长看板的资格口径，按账号事务和原有快照补缺，不发积分、不改余额；全部完成才写 `points-earning-c8-achievement-snapshots-v1`。在同一维护窗口配置 C8 后再恢复服务，避免快照与目录切换之间产生旧奖励承诺。重复运行直接返回，禁止在 C8 配置后重新固化旧奖励。
- 在同一维护窗口执行 [C8 帮助内容同步](../apps/server/migrations/20261023_points_earning_c8_knowledge.sql)，再配置 `POINTS_EARNING_C8_EFFECTIVE_DAY=YYYYMMDD` 和 `POINTS_EARNING_C8_EFFECTIVE_WEEK=YYYYWW`，选择未来的完整账号自然日和 ISO 周，通常使用同一个周一；边界不得早于对应的 C5/C6/C7 边界。完成快照准备后再配置并启用 `POINTS_EARNING_C8_ENABLED=true`，C5 总闸继续生效。应用启动缺边界或准备标记时失败关闭。帮助正文不复制奖励金额，恢复服务时刷新知识检索缓存。
- 已固化的日、周策略优先。C8 使用 `daily:c8:<YYYYMMDD>:<2|3>` 和 `week:c8:<YYYYWW>:<challenge>`；同一周期不会改用另一套 ref。回滚只关闭 C8 写闸，保留边界、快照、余额和周期锁；C8 新成就与已进入 C8 的任务周期暂停发奖，不回退旧规则。
- 激活前验证旧快照保护、C6 组合稳定、日周边界、单项与批量领取、重试幂等和暂停不回退。获取版本独立于消费目录，商店价格与每日惊喜不随 C8 调整。

## 有意义行为事实

C5 知识行动白名单为 `bookmark / note / file / todo / organize`；C6 每日创建待办另读 `todo_create`，不改变每周待办完成的口径。资源事务成功后写入不可变 `growth_events` 事实；待办完成和整理完成继续复用其不可变完成事件。

必须排除：游客、管理员预览、`adminContext`、`suppressUserRewards`、新手示例、系统回填、页面浏览、领取、抽奖、购买和管理员操作。事实 `meta` 只保存低敏感类型与布尔标记，不能保存标题、正文、URL、路径或原始内容。

每日和每周聚合统一查询 `growth_events(user_id, source, status, create_time)`，以账号时区计算自然日和 ISO 自然周。资源创建成功不能因为成长旁路失败而回滚；成长旁路也不能阻断既有 EXP/成就副作用。历史大表回填只允许由显式 migration 执行，禁止接回应用启动。

### 公开资源贡献成就

公开贡献以 `publicResources/achievements.js` 为目录事实源，五档为 1 / 10 / 50 / 200 / 500 项，对应「初次分享、开卷有益、星火传灯、聚知成林、知识灯塔」，积分为 10 / 30 / 80 / 150 / 300（合计 570）。这是新增的最终奖励预算，不再次按 C8 折半；500 档另需 Lv.8。50 / 200 / 500 档分别附带「传灯者、共读之光、知识灯塔」头像框。

计数复用公开资源可见性判定，只统计当前审核通过、未撤回、未下架、来源未删除的自有书签和纯文字笔记；书签按审核快照的规范化网址精确去重，笔记按来源 ID 去重。保存的公开副本与系统示例排除；修改、重复提交和重新公开不累加。当前符合条件的历史资源直接纳入进度，不自动批量发奖。

审核通过、公开内容变更、撤回、下架和删除来源时，在原事务内固化已达标成就；达到新等级时重算等级门槛。快照只记录资格，积分与装扮仍由统一领取事务到账，每档一次；已解锁或领取的成就永久保留。GET 仅计算进度，不补写快照；取消公开只降低未达成档位的当前进度。复用已有公开表、`user_achievements` 与积分/装扮账本，不增加 Schema 或历史数据迁移。

## 成就与补签卡

- C5/C6/C7 连签成就积分为 1/7/30/100/365 天对应 10/30/80/200/500；C8 对未来解锁奖励按上节减半。
- 连签里程碑奖励以 `growth.js` 的 `STREAK_MILESTONES` 为唯一配置，签到发放与成长页展示共用；调整只影响后续首次达成，已发积分、永久空间和领取事实不回收、不重算，断签后重新达成也不重复发放。后台策略模拟器的一次性池默认值须同步奖励总额。
- 高数量或陪伴类成就可叠加等级、有效活跃日门槛；页面必须完整展示数量、等级和活跃条件。
- 切换前已经满足旧条件的账号先固化解锁事实；已解锁奖励写入 `reward_points_snapshot`、`reward_frame_id_snapshot` 和 `policy_version`，领取时读取快照。
- 补签卡在首次正常签到达到连签里程碑时按 `STREAK_MILESTONES` 的递增数量赠送；正常升级至 5/10/15 级时各赠 1 张。每个里程碑仅赠一次，奖励数量调整只影响后续首次达成，不补发历史差额。也可通过积分兑换或积分抽奖获得，消费规则见[积分经济](./points-economy.md)。免费惊喜不发卡。持有数量不限，所有来源全量累积；历史已经结算的里程碑或因满仓未获得的赠卡不自动补发，已转换成积分的抽奖收据保留原结果。
- 每次补签消耗 1 张，仅修复按账号时区计算的今天之前最近 30 个自然日（不含今天，包含第 30 天，可跨月、跨年）的漏签与连签，不补经验、积分或里程碑奖励。阶梯“天数已达成”只表示当前连签达到门槛，不代表待领取或补签卡剩余数量，剩余卡数以当前库存为准。

## 周期切换与领取幂等

- 日规则按完整账号自然日切换，周规则按完整 ISO 自然周切换；禁止周中改版。
- `points_earning_period_policy` 固化每个日/周的规则版本。开关事故暂停后也不能让已到 C5 的周期回落旧规则并产生双领窗口。
- C5 每日 ref 为 `daily:c5:<YYYYMMDD>:<2|3>`，每周 ref 为 `week:c5:<YYYYWW>:<challenge>`；读取时兼容旧 ref，写入使用新 ref。
- 非消费发放使用 `points_grant_operations` 收据。相同账号与请求号只允许一个规范负载，扣/加余额、流水和成功结果必须在同一事务提交。
- Root 单用户积分/存储/补签卡调整与人工对账纠正同样复用收据；前端只在网络结果未知时保留并重放同一 `X-Request-Id`，服务端对同键异负载失败关闭。每次重放仍追加本次 intent/terminal 审计，但绝不再次写余额或流水。

## 用户积分明细与兑换目标

“成长中心”的「背包」统一展示余额与道具，正文切换「背包总览／积分明细」。余额概览位于页签上方，桌面三列、移动端紧凑分组；积分明细保留近 28 天收支摘要、完整收支筛选、详情与分页流水，不重复展示当前余额。收支分析和积分规则按需展开；同一来源的收入与支出分别聚合，不相互抵消。积分摘要受原功能开关控制，关闭或加载失败不影响流水查询。设置、工具箱、独立积分明细路由和旧积分中心／明细链接兼容进入背包的积分明细页签，关闭记录浮层回到原页面状态。

积分来源复用任务与成就名称字典，日常阶段展示发奖时的完成门槛。社区活动流水保存公开话题名称快照；旧记录按当前页批量关联话题名称，无法追溯时只显示通用类别。用户接口不透出后台发放备注、圈选条件或内部请求引用。

商品目标在「兑换」页设置，兑换成功后刷新目标余额、差额和可用状态。公开帮助由独立的 [积分明细帮助迁移](../apps/server/migrations/20260911_points_ledger_knowledge.sql) 幂等更新，不挂入应用启动。

- 目标商品必须来自实时服务端消费目录，不能在前端保存价格或限兑快照；下架或已经达到兑换上限的目标显示不可用并允许重新选择。
- 到达时间只使用近 28 天稳定收入估算，以 ±15% 区间展示，并明确不含未来消费、随机惊喜、成就和运营发放。
- 低压力模式隐藏预计天数，只显示余额、差额和进度。
- 用户摘要查询最多读取近 28 天流水，禁止为了卡片加载扫描账号全量历史；页面不轮询、不逐商品请求。
- 新增界面只使用自研 B 组件和 scoped 样式；不得新增全局 CSS 或页面级监听；明细复用同一份摘要和账本组件，兼容入口只负责导航。

## Root 积分治理 V2

积分治理后台保留单用户查询/调整，并增加健康总览、来源与去向、异常与对账、活动发放和只读模拟器。

- 时间范围仅支持 7/28/90 天或不超过 365 天的自定义窗口。
- 总览显示发行、消费、净发行、参与账号、余额分布和趋势；来源按策略分类，去向按商品/抽奖/其他消费分类。
- 每日净发行趋势必须能在指针悬停时显示日期、净发行、产出与消耗的精确数值；点击或键盘激活某个自然日后，展示该日按北京时间倒序的用户、积分增降、行为与时间。明细使用服务端日期绑定游标每批读取 50 条，前端虚拟渲染并在滚动触底时自动续查，不提供“加载更多”按钮；健康总览同时提供普通有效账号的当前积分余额 Top 20，点击用户直接进入有界的用户 360 来源、消费与流水视图。
- 用户 360 只按显式账号查询，并提供有界流水筛选；隐私字段和流水 `meta` 必须脱敏。
- 商品表现按经济版本和商品展示兑换人数、次数、消耗、历史首兑账号注册天数 P50、兑前余额 P50、成熟样本 30 天再消费率与头像框当前佩戴率。首兑画像排除时间窗前已有同商品成功兑换的账号，最多读取 5,000 个用户历史首单样本并标记截断；查询依赖 `idx_points_economy_user_status_time`。旧收据缺少余额结果时显示不可用，不回填猜测值。
- AI 加油余额实际消耗和永久空间真实使用增长在现有事实中无法归因到某次兑换；首期明确显示“待归因事实”，禁止用当前余额或当前占用倒推。只有未来建立不可变使用事实后才能开放这两项指标。
- 策略模拟器仅计算输入参数的理论结果，不写策略、不改余额、不生成领取事实。
- 异常结果是调查线索，不是封号结论。当前只展示能够由现有事实可靠证明的规则；需要跨期画像或审计事件的高级规则延后到日汇总/审计事实齐备后实现。

### 余额对账

迁移时用 `points_ledger_baselines` 固化 `当前余额 - 历史流水和`。后续期望余额为 `baseline_delta + points_log 全量和`。对账按游标批量扫描，禁止每用户 N+1。

默认只报告差异，不自动改 `user_growth.points`。人工确认后只能补写缺失的 `correction` 流水，使账本追上现有余额；修正前必须再次锁定并核对差值，重复请求幂等。禁止直接用对账任务覆盖余额。

## 背包获得记录

背包的「最近获得」与「获得记录」汇总各渠道实际到账的积分、永久 AI 额度、补签卡和永久扩容，覆盖签到、任务、成就、升级与连签里程碑、抽奖、管理员发放、活动、积分兑换和资源购买。按资产类型筛选，来源与到账去向明确展示；道具使用或余额消耗不删除原获得事实。抽奖页继续保留按次及十连组织的专用抽奖记录。

积分和 AI 复用各自账本；AI 预扣退回、历史余额初始化、账本对账纠正不属于新获得。补签卡和扩容发放在同一业务事务保存来源与实际数量，新增仅用于获得记录的零积分审计不进入普通积分列表；AI 包发放直接进入永久余额，旧背包包仍可转入。业务幂等回放不得再次发放或记账。

历史仅接入带实际数量的既有账本、成功抽奖／兑换收据、管理员成功终态审计与购买到账凭证；已写新资产账的收据不重复展示，管理员幂等重放审计不算再次获得。缺少数量或发放依据的旧记录不从当前余额、现奖励配置或持有权反推，不做读取时回填。用户接口只返回资产、实际数量、通用来源类别与时间，不返回内部引用、操作者、工单或后台备注。

## 安全活动积分发放

活动只允许正向积分，状态机固定为：

```text
draft → previewed → recipients_frozen → confirmed → running → completed | partial_failed
```

- 受众使用注册时间、最近活跃时间、等级、余额、明确账号与排除历史活动等结构化条件，或最多 5,000 个显式账号；不接受任意 SQL，默认排除游客、逻辑删除账号、非普通用户和有效安全封禁账号。
- 预览只返回人数、总积分、匿名样本、重名提示、余额分布影响和限额状态，不发积分。
- 冻结后名单不可漂移；每批冻结不超过 250，执行租约批次不超过 200，单收件人最多重试 5 次。
- 每个收件人使用稳定幂等请求号。发放事务同时写收据、余额、`campaign` 流水和成功状态；中断后可恢复。
- 激活前必须显式配置单活动人数、单用户积分和总积分上限；零值、负值、缺失值或超过硬上限一律失败关闭。
- 创建草稿必须携带客户端稳定请求编号；网络结果未知时复用原编号，服务端按“操作者 + 请求编号 + 负载哈希”返回原草稿，禁止重复创建或用同一编号替换负载。

## 表单提交奖励

- Root 在自己创建的公开收集中开启奖励，并显式填写每人积分及奖励名额；共享表单契约限定配置范围，最高支出为两者乘积。长期新用户来源调查通过[显式启用流程](./release-acceptance.md#新用户来源调查)将原表单名额设为 `null`，保留原每人奖励、答案、链接与发奖收据；普通表单管理接口不能新增不限名额奖励。开启奖励自动要求正式账号，填写者完成必填项并成功提交后自动到账，无需审核或再领取；回答内容不影响奖励额度。
- 每表单每账号只奖励一次；跨设备、更新答案和网络重试共用稳定 `collection-form:<formId>` 收据。回答、请求回执、积分收据、`campaign` 流水、余额及到账站内通知在同一事务提交，积分策略为 `collection-form-v1`，流水和通知保留公开表单标题快照。配置与名额在首次发布后锁定，不追补历史匿名提交。
- 首次发奖生成一条 `「{表单名称}」奖励已到账` 通知，名称使用发奖时的快照，点击进入积分明细；来源按账号与表单去重，修改答案、重放请求、已读或删除通知都不会重发积分或通知。桌面通知中心将其归入「成长与积分」，不进入 root 群发记录；外部推送复用通知队列与设备偏好，在事务提交后处理。
- 发放与表单关闭、删除按表单锁串行化；有限名额表单在最后名额发放后自动暂停，不能恢复已耗尽名额的表单。不限名额的来源调查不因奖励人数暂停。并发不会超发；成功请求在暂停后重放仍返回原结果。
- 删除或标记回答不扣回积分、不重置领取资格或释放已使用名额；删除表单也保留独立积分流水和发放收据。账号注销删除其填写内容，积分记录沿用既有治理保留规则。重复活动使用新表单，复制时奖励默认关闭。
- 复用 `grantPointsIdempotently`，不复用后台批量 Campaign 的名单冻结与执行状态机。收集者可查看奖励人数、总积分以及每份回答对应账号和到账积分；用户积分明细只展示公开来源名称。

## 社区发帖活动奖励

- 由社区管理的 Root 话题配置开启，独立于充值活动和后台定向批量 Campaign。每话题每账号一次；经验 0–1000、积分 0–10000，至少一项大于零；活动窗口按提交修订时间判断，起始包含、截止不包含。未配置不发奖，不追溯旧帖。
- 帖子审核公开的同一事务写入 `community_task_awards`，固定当时奖励。活动结束后批准窗口内提交的帖子仍可达成。产生完成记录后禁止修改窗口或奖励额度；关闭话题或发帖任务停止新达成，已达成的领取资格保留。
- 广场／话题页领取与 `growth/claimAll` 的 `community` 分组共用服务；工作台、成长中心的一键领取默认包含该组。领取时再次锁定并核验完成帖子仍公开、属于本人且保留对应话题；不满足时暂不可领。再次发布合格帖子可以恢复未领取资格；已领取收据不变。
- EXP 走 `grantExp`，来源 `community_task`，不受日常经验上限截断；积分走 `earnPoints`，原因 `campaign`、策略 `community-task-v1`。两者引用均为 `community-task:<topicId>`，与后台批量 Campaign 的收据区分。余额、两种账本与领取时间在一笔事务提交，失败整体回滚，重复请求不重复发放。
- 配置、奖励记录由显式迁移 `20260916_community_task_rewards.sql` 安装，上线前执行 Schema 门禁。不得通过本地示例默认给正式活动填入奖励。发放后撤回帖子不自动扣回资产，作弊处理沿用治理流程。

## Schema、迁移与激活

应用启动的 `ensureGrowthCenterSchema()` 只补幂等表、列和索引，不扫描历史业务表。历史兼容由 `20260814_points_earning_c5.sql` 在维护窗口显式完成：

1. 固化旧成就承诺与奖励快照；
2. 回填低敏感有意义行为事实；
3. 捕获余额对账期初基线；
4. 写入三个迁移标记。

运行时开关与边界：

- `POINTS_POINTS_CENTER_ENABLED`
- `POINTS_ADMIN_GOVERNANCE_V2_ENABLED`
- `POINTS_EARNING_C5_ENABLED`
- `POINTS_EARNING_C5_EFFECTIVE_DAY=YYYYMMDD`
- `POINTS_EARNING_C5_EFFECTIVE_WEEK=YYYYWW`
- `POINTS_CAMPAIGN_ENABLED`
- `POINTS_CAMPAIGN_MAX_RECIPIENTS`
- `POINTS_CAMPAIGN_MAX_POINTS_PER_USER`
- `POINTS_CAMPAIGN_MAX_TOTAL_POINTS`

所有布尔开关未知值按关闭解析。推荐依次开启：积分中心 → 治理只读 → 下一个完整日/周的 C5 获取 → Campaign。Campaign 必须最后开启，且依赖治理 V2 和三个正数安全上限。

回滚优先关闭获取写闸或 Campaign，不删除新表、不撤销资产、不清理周期锁。已经进入 C5 的日/周不能切回旧策略；事故期间宁可暂停新发放，也不能制造同周期双领。

## 性能与验收底线

- 高频用户摘要仅扫 28 天；后台查询有最大时间窗、分页/游标和硬 LIMIT；商品画像最多 5,000 个首兑用户样本；活动执行有批次与租约。余额分布和受众余额筛选使用 `user_growth(points, user_id)` 索引。
- 首期不新增复杂积分数仓。连续观察到后台聚合超出预算后，再以不可变账本增量生成日汇总，不能先建无人使用的双写口径。
- 每日两个独立事件、周期锁、旧成就快照、补签卡来源、发放幂等、Campaign 恢复、对账只报告、Root 权限与隐私过滤必须有自动测试。
- 按 [变更级验证](./release-acceptance.md#变更级验证) 执行受影响前后端与 Schema 门禁，界面遵守 [开发规范](./development.md) 的组件与样式约束。
- 知识库与本文必须和代码同批更新。任何数值调整都升级获取策略版本，不能原地改写 C5 快照。
