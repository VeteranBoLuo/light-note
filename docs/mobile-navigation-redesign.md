# 轻笺移动端双层导航落地方案

## 1. 结论

移动端采用“顶部资源切换 + 底部全局导航”是合适的，但两层必须承担不同职责：

- 顶部只切换同一工作区内的资源类型：书签、笔记库、云空间。
- 底部只放跨模块的全局入口：资料、待处理、AI、搜索、我的。
- 详情、编辑、文件预览等沉浸式页面不显示顶部资源切换；是否显示底部导航由页面层级决定。

这样既能获得原生 App 常见的高频切换体验，又不会出现上下两处重复放置“书签 / 笔记 / 云空间”的信息噪声。

## 2. 当前问题

当前移动端会根据“默认首页”只在书签、笔记库、云空间中的一个页面保留全局顶部导航，另外两个模块则表现为带返回箭头的次级页面。由此带来三个问题：

1. 三个同级资源模块在视觉层级上不平等。
2. 从书签到笔记或云空间通常需要绕到个人中心，切换路径过长。
3. 移动端缺少稳定的全局落点，用户容易把浏览器返回误当作模块切换。

## 3. 信息架构

### 3.1 顶部资源切换

固定顺序：

| 标签 | 路由 | 语义色 | 说明 |
| --- | --- | --- | --- |
| 书签 | `/home` | 书签紫 | 保存和浏览网页资源 |
| 笔记库 | `/noteLibrary` | 笔记绿 | 创建和管理笔记 |
| 云空间 | `/cloudSpace` | 文件橙 | 管理上传文件 |

交互规则：

- 使用文字标签加短下划线表示当前模块，不使用三块厚重胶囊按钮。
- 切换时走 Vue Router，不刷新页面，不重建全局状态。
- 每个模块记住最近一次滚动位置、筛选条件、搜索词和视图模式。
- 再次点击当前标签时，列表回到顶部；是否同时清空筛选由各模块已有“标题点击重置”行为决定，不能隐式清空用户条件。
- 顶部切换条固定在全局顶栏下方，内容滚动时不产生可透出的缝隙。

### 3.2 底部全局导航

建议固定为五项：

| 入口 | 行为 | 激活范围 |
| --- | --- | --- |
| 资料 | 回到最近使用的书签、笔记库或云空间 | `/home`、`/noteLibrary`、`/cloudSpace` |
| 待处理 | 进入待处理箱 | `/inbox` |
| AI | 打开现有 AI 工作区，不新增一套聊天实现 | AI 工作区打开期间 |
| 搜索 | 进入跨模块资源中心 | `/search` |
| 我的 | 进入个人中心 | `/personCenter` |

“资料”不是一个新的内容页，而是三个资源模块的导航分组入口。它默认落到用户设置的移动端首页，之后优先回到本次会话最近访问的资源模块。

AI 保持为全局工作区：点击底部 AI 入口调用现有 `openAiAssistant()`，继续复用当前会话、附件、上下文和流式状态，不把它改造成与现有悬浮 AI 并存的第二套页面。

## 4. 页面显示规则

### 4.1 同时显示顶部切换和底部导航

- 书签列表
- 笔记库列表
- 云空间列表

### 4.2 只显示底部导航

- 待处理
- 资源中心
- 个人中心
- 设置、成长等可安全保留全局落点的一级页面

### 4.3 两层都隐藏

- 笔记详情与编辑
- 新增或编辑书签
- 文件全屏预览
- 登录、注册、授权回调
- 全屏弹窗、图片查看器和系统文件选择器

详情页继续使用明确的返回按钮。返回时优先回到来源列表，并恢复来源模块的滚动和筛选状态。

## 5. 布局与尺寸

- 仅在手机断点 `< 768px` 启用，平板和 PC 保持现状。
- 全局顶栏高度保持 `60px`，资源切换条建议 `44px`。
- 底部导航视觉高度建议 `56px`，另加 `env(safe-area-inset-bottom)`。
- 页面可滚动区域统一由移动端壳计算：

  `100dvh - 顶栏 - 资源切换条（按需）- 底栏 - 安全区`

- 底栏使用实色主题背景和顶部细分隔线，不使用容易造成视觉色差的重阴影。
- 所有图标从 `apps/web/src/config/icon.ts` 获取，通过 `SvgIcon` 渲染；交互控件统一使用 B 系列组件。
- 键盘弹出时隐藏底部导航，避免输入区被二次抬升；键盘关闭后恢复。

## 6. 路由与状态设计

新增一个移动端壳层状态模型，不把导航判断散落到各业务页面：

```ts
type MobileShellSection = 'resources' | 'inbox' | 'ai' | 'search' | 'profile';
type MobileResourceRoute = '/home' | '/noteLibrary' | '/cloudSpace';
```

路由 `meta` 建议增加：

```ts
meta: {
  mobileShell: 'resources',
  mobileTopSwitcher: true,
  mobileBottomNav: true,
}
```

详情和编辑页显式声明 `mobileBottomNav: false`。壳层只读路由元信息决定布局，不再使用“是不是用户默认首页”推导顶部导航是否出现。

资源状态分两层保存：

- 已有业务状态继续留在各 Pinia store，例如标签筛选、搜索词、列表数据和视图模式。
- 导航壳只保存 `lastMobileResourcePath` 和三个列表的滚动位置，不复制业务数据。

登录用户的默认移动首页继续读取现有 `preferences.homePage`；“最近访问模块”只需保存在当前设备本地，不必同步到后端。

## 7. 组件落点

建议新增：

- `apps/web/src/components/mobile/MobileAppShell.vue`
- `apps/web/src/components/mobile/MobileResourceTabs.vue`
- `apps/web/src/components/mobile/MobileBottomNav.vue`
- `apps/web/src/config/mobileNavigation.ts`
- `apps/web/src/composables/useMobileNavigationState.ts`

建议修改：

- `apps/web/src/view/index.vue`：统一承载手机端壳和内容区高度。
- `apps/web/src/components/home/navigation/Navigation.vue`：从“默认首页专属”调整为移动端全局顶栏。
- `apps/web/src/components/home/navigation/RightArea.vue`：与底部“我的”入口去重，资源列表顶栏只保留搜索和必要状态。
- `apps/web/src/utils/preferences.ts`：保留默认首页解析，拆除其对导航显隐的控制。
- 三个资源列表页：移除因“不是默认首页”产生的返回箭头，接入滚动恢复。
- `apps/web/src/config/icon.ts` 与中英文语言包：补齐底部导航图标和文案。

不建议把顶部、底部导航分别写进书签、笔记库、云空间三个页面，否则后续高度、主题和安全区会再次出现不一致。

## 8. 分阶段实施

### 第一阶段：壳层和底部导航

1. 建立路由元信息和统一移动端壳。
2. 接入资料、待处理、AI、搜索、我的五个入口。
3. 处理安全区、键盘、全屏页显隐和浏览器/PWA 返回。
4. 保持三个资源页现有内容布局不变。

### 第二阶段：顶部资源切换

1. 接入书签、笔记库、云空间切换条。
2. 移除三个资源页之间的返回层级。
3. 恢复每个模块的筛选、搜索、视图和滚动位置。
4. 处理切换中的加载骨架，避免页面闪白或旧内容串页。

### 第三阶段：细节收口

1. 调整资源页标题区与顶部切换条的间距。
2. 统一浅色、深色主题的背景、分隔线和激活色。
3. 在 Chrome、Edge、Safari 等移动浏览器以及 PWA 独立窗口中分别验收。
4. 根据真实使用数据判断是否保留顶栏的全局搜索入口。

## 9. 验收标准

- 360px、390px、430px 三种常见手机宽度无横向溢出。
- 书签、笔记库、云空间可在两次点击以内互相切换。
- 模块切换后原筛选、视图和滚动位置不丢失。
- 顶部标题、筛选按钮和新增按钮不随内容列表滚走，也没有内容从固定区缝隙透出。
- 浅色和深色主题下边框、背景、激活色与 Web 移动端一致。
- 浏览器/PWA 返回先关闭抽屉、弹窗和 AI，再回详情来源，最后才离开轻笺。
- 输入法弹出时底部导航不遮挡编辑器、搜索框或 AI 输入框。
- 平板与 PC 的路由、导航和布局不发生变化。
- 浏览器访问与 PWA 独立窗口使用同一套移动端壳，不依赖客户端专属 CSS 补丁。

## 10. 建议的实施边界

第一轮只实施“导航壳、显隐规则和路由切换”，不同时重做三个业务页面的卡片视觉。导航稳定后再逐页收口间距和动效，可以显著降低滚动容器、固定定位和移动浏览器视口高度计算互相影响的风险。
