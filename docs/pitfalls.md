# 轻笺踩坑与回归防护记录

本文档记录开发、测试、部署和运维中已经真实发生，且具有复发风险或反直觉根因的问题。它不是需求清单，也不是临时排障日志；目标是把一次排障得到的证据沉淀为以后可以直接执行的约束、测试和验收步骤。

## 使用规则

1. 开始开发或排障前，先按模块、症状和关键词搜索本文档；命中已有记录时优先遵守其中的防回归约束。
2. 一旦确认了具有复发价值的坑，必须在同一轮任务中记录或更新本文档，不能只把结论留在聊天、提交说明或个人记忆中。
3. 同一根因再次出现时更新原条目，补充新的表现、触发条件和回归测试，不重复创建含义相同的记录。
4. 每条记录至少包含：现象、影响范围、误导线索、根因、修复、防回归约束、验证方法和相关代码。
5. 尚未证实的猜测要明确标记为“待验证”，不能混入已确认根因；修复上线后补充最终状态和必要的提交引用。
6. 禁止记录密码、Token、Cookie、连接串、用户正文、私有对象地址等敏感信息；线上案例只保留脱敏后的规模、耗时和稳定标识。

以下情况必须记录：

- 引发线上回退、数据错误、安全风险或明显性能劣化的问题；
- 只在特定账号规模、移动端、WebView、浏览器、主题、语言或生产环境出现的问题；
- 表面原因与真实原因不一致，容易让后续开发者再次误判的问题；
- 需要跨前端、后端、Schema、Worker、缓存或部署链路才能解释的问题；
- 曾采用但被证明会适得其反的“优化”或兼容方案。

普通文案错别字、一次性需求变更和没有复发价值的机械修正无需单独建条目。

### LN-PIT-019：爱发电 Webhook 验签成功不等于下单归属可信

- 日期：2026-08-13
- 状态：已修复待上线
- 影响范围：爱发电下单凭证归属、OAuth 历史订单合并、Webhook 重推与订单同步
- 关键词：Webhook、RSA、custom_order_id、query-order、唯一订单、OAuth、冲突归属

#### 现象

计划通过下单 URL 的 `custom_order_id` 携带轻笺随机码，再从爱发电 Webhook 读取该字段，把订单直接归入轻笺用户。这样看似已有 RSA 验签，又能立即确认赞助者。

#### 误导线索与排除项

- Webhook 整体带有 `sign`，但这不表示 JSON 中每个字段都进入了签名文本。
- 随机码不可猜只能证明它来自某次轻笺下单跳转；如果读取它的载荷字段未被签名保护，仍不能把 Webhook 当成归属事实。
- OAuth 后重新插入“已绑定订单”会让同一爱发电订单在未绑定记录与绑定记录中各出现一次，问题不在前端去重，而在订单事实没有唯一主键。

#### 已确认根因

爱发电官方 Webhook 的 RSA 签名文本只按顺序拼接 `out_trade_no + user_id + plan_id + total_amount`，不包含 `custom_order_id`、`status`、`month` 等字段。因此验签成功只可确认这四个签名字段，不能证明回调里的轻笺随机码可信。Webhook 还可能重推且不保证及时送达，单靠回调也无法完成历史订单归并。

#### 修复方式

- Webhook 验签成功后只按唯一 `provider_order_no` 幂等落一条 pending 订单，不读取回调里的随机码做归属。
- 服务端随后用爱发电 API Token 调用 `query-order(out_trade_no)`；只有 API 返回的 `custom_order_id` 才可匹配轻笺保存的 SHA-256 凭证摘要。
- `support_orders.provider_order_no` 建唯一索引；Webhook、全量 API 同步与 OAuth 绑定都更新同一行。
- OAuth 与下单凭证指向同一轻笺用户时把证据来源升级为 `oauth_checkout`；指向不同用户时保留已有归属并标记 `conflict`，禁止静默转移。
- Webhook 原始载荷跳过通用日志和通用攻击正文检测，但仅限精确 POST 路径；仍保留 IP 限流、严格字段边界、RSA 验签和 API 二次复核。

#### 防回归约束

1. 第三方回调只能信任其官方签名规范明确覆盖的字段；新增字段必须先确认是否进入签名文本。
2. 任何支付/赞助归属都必须以第三方订单号作为唯一事实，不得按“未绑定订单”和“OAuth 订单”拆成两张可重复账本。
3. `custom_order_id` 只保存随机值的摘要，禁止携带用户 ID、邮箱或昵称；OAuth Secret 与 API Token 只存在服务端环境变量。
4. 第三方自由文本载荷若需绕过通用检测，只能用精确方法 + 精确路径，并由路由补齐限流、验签和二次复核，禁止放宽整个模块。
5. OAuth 不是赞助前置条件；解绑只能撤销 OAuth 证据，不能删除仍有可信下单凭证支持的订单归属。

#### 验证方法

- 单测断言改变 `custom_order_id` 不会改变官方 Webhook 签名文本，防止以后误把它当成已签名字段。
- 单测覆盖同一用户的下单凭证 + OAuth 合并为一个归属，以及两个用户证据冲突时不转移。
- Schema 测试和数据库门禁断言 `uk_support_order_provider`、`uk_support_checkout_token` 及账号关联唯一索引存在。
- 安全策略测试断言只跳过 `/support/afdian/webhook` 的精确 POST，GET、OAuth 接口和相似路径仍进入通用检测。

### LN-PIT-008：本人换头像框后聊天室仍显示旧装扮

- 日期：2026-08-13
- 状态：已修复待上线
- 影响范围：桌面端和移动端社区聊天室中当前用户自己的历史及新发消息
- 关键词：头像框、共享状态、消息快照、响应式、性能

#### 现象

用户在顶栏或成长中心佩戴、切换、卸下头像框后，顶栏会立即更新，但聊天室里自己的消息仍显示进入频道时的旧头像框，刷新页面后才恢复一致。

#### 已确认根因

聊天消息 DTO 中的 `author.frameId` 是拉取消息时的展示快照；聊天室一直直接渲染该字段。头像框操作已经更新模块级 `growth.equippedFrame`，但聊天室没有把本人这种当前会话内可变的外观字段解析到共享状态，因此旧消息对象不会变化。

#### 修复方式

- 本人消息在成长状态已加载时优先使用共享 `growth.equippedFrame`，其他用户继续使用消息快照。
- 共享状态尚未加载时回退消息快照，避免首屏头像框闪空；状态已加载且值为 `null` 时把它作为明确的卸下状态。
- 不新增接口请求、定时器、watch、全局事件或 WebSocket 广播，只复用已有模块级响应式状态。

#### 防回归约束

1. 当前用户在本地已经拥有权威共享状态的低频外观字段，应优先从共享状态渲染本人视图，不能依赖页面 DTO 的旧快照。
2. “状态尚未加载”和“已加载但明确为空”必须分开处理，否则卸下装扮会错误回退旧框。
3. 不要为了本人即时反馈广播全体用户外观更新；其他用户继续随正常消息刷新或页面重进更新，避免扩大实时协议与重绘范围。

#### 验证方法

- 组件测试同时渲染本人和他人消息，动态切换共享头像框并卸下，断言只有本人节点即时变化。
- 运行 `pnpm --filter web exec vitest run src/view/communityChat/CommunityChatWorkspace.test.ts` 和 `pnpm --filter web typecheck`。

### LN-PIT-007：Markdown 编辑与预览换行不一致导致正文横向溢出

- 日期：2026-08-13
- 状态：已修复待上线
- 影响范围：桌面端 Markdown 笔记编辑，尤其是默认“编辑 + 预览”分栏
- 关键词：Markdown、CodeMirror、lineWrapping、软换行、分栏、横向滚动、源码换行

#### 现象

- Markdown 正文中的长逻辑行不会在编辑区右边界自动折行，而是继续向右延伸。
- 默认分栏下，编辑文字会越过左侧编辑区的可见范围，看起来与右侧预览内容重叠。
- 编辑区修复软换行后，预览区的普通长连续字符仍会撑宽内容并出现横向滚动条，两侧换行时机不一致。
- 移动端和窄分栏更容易放大上述问题。

#### 误导线索与排除项

- **不是 Markdown 源码缺少真实换行。** 即使用户只输入一个很长的自然段，编辑器也应按可用宽度做视觉软换行，数据库仍保存原始逻辑行。
- **不是分栏容器缺少 `min-width: 0`。** 编辑区、预览区和 CodeMirror 根节点已经具备收缩约束。
- **不是预览层覆盖编辑层。** 文字来自 CodeMirror 自身横向延伸的逻辑行。

#### 已确认根因

CodeMirror 的 `EditorView.lineWrapping` 曾被条件化为只在 `props.mobile` 为真时启用，桌面端明确关闭软换行。默认桌面视图又是左右分栏，单个逻辑行可用宽度更窄，因此正常自然段很容易产生横向滚动和视觉越界。现有测试还断言桌面端必须关闭 `cm-lineWrapping`，把错误体验固化成了回归门禁。

编辑区启用软换行后，Markdown 预览根容器仍未声明长连续字符的断行规则。浏览器会把无空格英文、长 ID 或 URL 作为不可拆分的最小内容宽度，使普通段落撑出预览栏；`pre` 的默认 `white-space: pre` 又会阻止代码长行折行。预览容器允许 `overflow: auto`，最终表现为整栏横向滚动条。不能用全局隐藏溢出来掩盖问题，否则只会截断内容。

#### 修复方式

- Markdown 编辑器在桌面端和移动端统一启用 `EditorView.lineWrapping`。
- 移除只为端差异服务的 wrapping compartment 和监听；断点变化不再改变正文换行语义。
- 回归测试同时断言两端启用软换行，并确认编辑器取值仍与原始 Markdown 完全一致。
- 编辑区与预览区共用 Markdown 字体、字号、行高和水平/顶部内边距变量，预览首个块级元素清除顶部外边距，保证首行正文从同一基线起排。
- 预览普通正文、链接和表格单元格使用 `overflow-wrap: anywhere`，并保留 `word-break: break-word` 兼容回退；代码块使用 `white-space: pre-wrap` 保留源码换行和缩进，同时让长行按预览栏宽软换行。

#### 防回归约束

1. Markdown 写作区必须按自身可用宽度软换行，不能因为桌面端允许横向滚动就关闭正文折行。
2. 软换行只属于编辑器视觉布局，不得向源码插入换行符，也不得改变撤销历史或保存内容。
3. 分栏、单编辑和移动视图必须使用同一换行语义；端差异只调整字号、间距和触控行为。
4. 调整 CodeMirror 扩展时，测试必须同时检查 `.cm-content.cm-lineWrapping` 和 `getValue()` 源码完整性。
5. 编辑区与预览区的字体、字号、行高和正文起点必须来自同一组 `--note-markdown-*` 变量；禁止在两侧重新写两套常量。
6. 预览普通正文和代码块都不得因长行撑宽整栏；代码块必须保留源码换行与缩进，并按当前栏宽软换行。复杂图表等无法断行的结构化内容才由自身滚动容器承接。

#### 验证方法

- 组件测试分别挂载桌面端与移动端编辑器，断言两者均启用 `cm-lineWrapping`，且长逻辑行源码没有被改写。
- 人工在桌面“编辑 + 预览”模式输入超过左栏宽度的中文自然段和长 URL，确认内容在分栏边界内折行且不出现横向覆盖。
- 分别输入无空格英文、长数字/ID、普通链接、包含长值的表格和长代码行，确认预览区均按自身栏宽折行且不出现整栏横向滚动；代码块的显式换行和缩进仍被保留。
- 在分栏顶部对照普通段落的第一行，确认编辑与预览文字使用相同字体、字号、行高并位于同一纵向起点；首个元素为标题、列表、引用或代码块时不得被统一规则裁掉其必要内部样式。
- 切换“仅编辑 / 编辑 + 预览 / 仅预览”后再次读取正文，确认没有新增非用户输入的换行。

### LN-PIT-006：待整理状态不能由入口参数代替数据库事实

- 日期：2026-08-13
- 状态：已修复待上线
- 影响范围：PC 笔记库预览与笔记详情编辑页；移动端详情更多菜单
- 关键词：待整理、resource_inbox、isPending、路由参数、详情接口、预览副本、列表缓存、状态一致性

#### 现象

- 笔记库卡片正确显示“待整理”，进入同一篇笔记的预览或编辑页后却看不到该状态。
- 正式编辑页没有加入或取消待整理的入口；预览页虽然复用了列表菜单，但操作不易发现，且可能只更新预览副本，退出后卡片仍显示旧状态。
- 只有从待整理页面携带 `?organize=inbox` 进入编辑页时才出现整理横幅，普通入口无法反映数据库里的真实状态。

#### 误导线索与排除项

- **不是待整理关系没有保存。** 列表通过 `resource_inbox` 回填的角标正确，数据库关系本身存在。
- **不是必须额外调用一次待整理接口。** 详情读取已经知道当前用户和笔记 ID，可以在同一条详情 SQL 内完成索引点查。
- **不是单纯少放一个胶囊。** 如果详情、预览副本和列表缓存各自维护状态，即使补了 UI，切换后仍会出现互相覆盖和返回列表回退的问题。

#### 已确认根因

详情接口只返回 `note` 正文和目录能力，没有聚合 `resource_inbox` 的真实状态；编辑页则把路由来源 `route.query.organize === 'inbox'` 当成了资源状态。路由参数只能说明用户从哪里进入，不能证明关系当前仍为 `pending`。

桌面预览从列表对象浅拷贝出 `previewNoteSeed`。待整理切换成功后若只修改这个副本，当前卡片和 Pinia 列表快照不会自动同步；另一方面，已经返回的详情预取仍可能携带旧状态，进入编辑页时又会把新状态覆盖回去。

#### 修复方式

- 详情 SQL 在原查询内使用 `EXISTS` 聚合 `resource_inbox`，返回布尔值 `isPending`；查询命中 `(user_id, resource_type, resource_id)` 唯一索引，不新增网络或数据库往返。
- PC 预览和编辑顶栏显示统一的 `InboxPendingBadge`；桌面、平板和手机更多菜单均复用 `useInboxEnqueue` 加入或取消待整理。
- 切换成功后同步当前列表、预览副本和同账号列表快照，并失效携带旧状态的详情预取；离开编辑页时把新状态写入短期详情快照。
- “保存并完成整理”只由真实 `isPending` 决定，并放入既有面包屑栏右侧，不再新增整行横幅或挤压编辑区；完成后立即清除当前状态和列表缓存角标。
- 路由入口只决定完成后的去向：从待整理页进入则返回待整理页，从笔记库普通进入则留在当前编辑页。

#### 防回归约束

1. 资源工作流状态必须来自服务端权威关系，不得用路由参数、页面来源或按钮可见性推导。
2. 详情首屏需要的轻量关系状态应优先聚合进原详情查询；禁止为单个布尔值增加串行接口，重新拉长骨架屏。
3. 页面内切换跨列表状态时，必须同时处理当前对象、预览副本、列表快照和详情预取，不能只修改触发按钮持有的对象。
4. 路由参数只控制入口相关流程和完成后的返回目标，不得参与待整理状态、胶囊或完成按钮的显示判断。
5. 只读或分享详情不得暴露待整理写操作；新建未落库笔记也不得显示关系操作。

#### 验证方法

### LN-PIT-005：Markdown 资源选择器的上下键被编辑器截断

- 日期：2026-08-13
- 状态：已修复待上线
- 影响范围：桌面端 Markdown 笔记编辑；通过 `@` 打开的行内资源选择器
- 关键词：Markdown、CodeMirror、资源选择器、ArrowUp、ArrowDown、Enter、keymap、事件优先级

#### 现象

- Markdown 模式输入 `@` 打开资源选择器后，上下键仍移动正文光标，不能切换候选资源；回车也可能继续编辑正文。
- 同一个资源选择器在富文本模式下可以正常使用上下键和回车。
- Markdown 外层处理函数已经包含 `preventDefault()` 和候选移动逻辑，因此只阅读业务函数容易误判为功能已经完整接入。

#### 误导线索与排除项

- **不是资源查询或候选列表状态异常。** 鼠标可以选择资源，候选项及 `moveActive()` 本身正常。
- **不是缺少 `preventDefault()`。** Markdown 父组件已经调用该方法，但事件没有到达父组件处理函数。
- **不是 TinyMCE 与 CodeMirror 共用状态冲突。** 富文本使用捕获阶段监听，能在编辑器默认行为前处理按键。

#### 已确认根因

Markdown 从普通文本框迁移到 CodeMirror 后，仍沿用父组件 `@keydown` 处理资源选择器。`MarkdownCodeMirror` 通过普通优先级的 `EditorView.domEventHandlers` 向外转发事件，而 CodeMirror 默认 keymap 同样处于默认优先级且更早注册。

`ArrowUp`、`ArrowDown` 和 `Enter` 命中默认 keymap 后会被直接认领，后续 DOM handler 不再执行。结果是外层资源选择逻辑虽然存在，却收不到这些按键；这也是富文本正常而 Markdown 异常的关键差异。

#### 修复方式

- 使用 `Prec.highest(EditorView.domEventHandlers(...))` 提升外部事件桥优先级，让资源选择器先决定是否消费按键。
- 外层调用 `preventDefault()` 时，事件桥返回已处理，CodeMirror 不再执行默认光标移动或换行。
- 外层没有消费事件时返回未处理，CodeMirror 默认 keymap 继续执行，普通编辑体验不变。
- 继续保留 `event.isComposing` 判断，输入法候选确认不进入资源选择器键盘逻辑。

#### 防回归约束

1. CodeMirror 上的浮层、补全或业务快捷键不能只挂 Vue 外层 `keydown`；必须明确其与 CodeMirror keymap 的优先级。
2. 只有浮层处于有效打开态时才消费导航键；关闭后必须把按键交还编辑器默认行为。
3. 键盘回归不能只断言业务处理函数存在，要真实向 `.cm-content` 派发事件并同时验证外层回调和正文结果。
4. 调整 CodeMirror 扩展顺序、keymap 或 DOM 事件桥时，必须回归 Markdown 的 `@` 选择器、撤销重做、查找和普通换行。

#### 自动回归门禁

- `MarkdownCodeMirror.test.ts` 断言外部资源选择器可以在默认 keymap 前接收并拦截上下键与回车。
- 同一测试关闭拦截后再次按回车，断言 CodeMirror 仍正常执行默认换行，防止修复扩大为全局按键屏蔽。

#### 人工验证方法

1. 打开 Markdown 笔记，输入 `@` 并等待资源候选出现。
2. 连续按上下键，确认高亮候选移动且正文光标位置不变。
3. 按回车插入当前资源，正文不产生额外换行；按 Esc 可关闭选择器。
4. 关闭选择器后按上下键和回车，确认正文光标移动与换行恢复正常。
5. 在富文本模式重复 `@` 选择，确认既有键盘交互没有退化；中文输入法组词和回车确认不被误拦截。

1. 同一个叶子字段名在不同接口具有不同类型时，不得直接放宽全局字段分类；应使用方法、规范化路径、完整字段和服务端合法值共同限定例外。
2. 路由级安全检测白名单必须同时测试合法值和反例，至少覆盖非法枚举、错误路径和错误方法。

- **不是移动端覆盖层或 history 竞争。** 该页面没有先关闭浮层再导航，公共浮层交接规则与本问题无关。

#### 已确认根因

`AdminDataPage` 的组合页在桌面端由 `.admin-data-page__table` 承担纵向滚动；在 `max-width: 960px` 下，为了让长内容自然展开，内层改为 `overflow: visible`，真正的滚动容器切换成外层 `.admin-data-page`。

总览下钻代码固定对 `.admin-data-page__table` 调用 `scrollTo()`。生产移动视口实测外层 `scrollHeight = 4603 / clientHeight = 844`，内层 `scrollHeight = clientHeight = 4496`；因此调用落在不可滚动元素上，外层 `scrollTop` 始终为 0。

#### 修复方式

- 在 `utils/zoom.ts` 增加 `findVerticalScrollContainer()`，从目标向上查找计算样式允许纵向滚动且真实溢出的最近祖先。
- 后台总览先解析当前断点下的实际滚动祖先，再复用已有 `scrollIntoContainer()` 完成缩放兼容的定位。
- 没有祖先真实溢出时保留原内容区作为 fallback，避免短内容页面产生空容器。

#### 防回归约束

1. 响应式页面会切换滚动层级时，不得用固定 class 假定滚动容器；应按当前 DOM 的 overflow 与真实溢出解析，或由公共壳显式暴露滚动容器。
2. 下钻入口的测试不能只断言 click handler 和筛选状态，还要断言最终 `scrollTo()` 作用于当前实际溢出的容器。
3. 修改 `AdminDataPage` 的移动端 overflow、组合页布局或断点后，必须同时回归页面内锚点、筛选下钻和返回顶部。
4. “点击后状态变化但界面无反馈”应分别检查事件、数据和可见定位，不要只从按钮事件或接口错误入手。

#### 自动回归门禁

- `utils/zoom.test.ts` 分别构造桌面“内层滚动”和移动“内层展开、外层滚动”，断言解析到正确容器。
- `AdminOverview.metrics.test.ts` 断言今日五类下钻继续使用实际滚动容器解析和统一缩放滚动函数。

### LN-PIT-001：移动端笔记库首次进入详情出现长时间骨架屏

- 日期：2026-08-13
- 状态：已修复并上线
- 影响范围：Android App、移动浏览器和 PWA；笔记较多的账号最明显
- 关键词：笔记库、笔记卡片、详情骨架屏、冷缓存、大账号、正文摘要、DOM 解析、TinyMCE、CodeMirror、预加载、WebView 主线程
- 修复提交：`ba742a9d`

#### 现象

- App 完全关闭后重新打开，从笔记库第一次进入未打开过的笔记，骨架屏通常持续 1～3 秒，极端情况下移动浏览器会卡住 10 秒以上。
- 同一篇笔记打开过一次、有缓存后明显变快；切换到笔记很少的游客账号时，未缓存笔记也通常只需几百毫秒。
- 笔记较多的 Root 账号稳定慢于游客账号，说明耗时会随列表规模放大；桌面浏览器不明显，移动 WebView 最明显。
- 用户直觉上认为“点击一张卡片进入详情，不应与外面有多少张卡片有关”，从业务关系看是对的，但旧实现让列表和详情争用同一条浏览器主线程，形成了间接耦合。

#### 误导线索与排除项

- **不是详情 SQL 或目录八层链路的主要耗时。** 详情接口本身可以在几十至百毫秒量级返回；接口返回后，WebView 仍可能因为主线程繁忙而无法及时导航和绘制。
- **不是缺少数据库迁移。** 本次核心修复是向后兼容的列表响应协议和前端加载策略，不新增表或字段；把长骨架屏首先归因于“线上漏迁移”会偏离主因。
- **卡片数量不会直接拖慢详情查询，但会拖慢详情的可见时间。** 网络请求、JSON 处理、响应式更新、富文本解析、模块解析和页面绘制最终都需要浏览器主线程参与。
- **图片预览不是主因。** 卡片只加载一张服务端压缩缩略图，并使用懒加载、异步解码和低请求优先级；禁止为了排障重新返回原图或一次加载正文全部图片。

#### 已确认根因

##### 1. 列表把每张卡片的正文解析成本留在了移动端

旧分页接口虽然每页只返回 48 张卡片，但仍会为每张卡片返回最多 4000 字符的 `content` 正文前缀。前端每个卡片组件随后分别执行：

1. 按笔记类型加载 Markdown/HTML 转换逻辑；
2. 执行富文本净化；
3. 创建临时 DOM 并遍历节点提取摘要和首图位置；
4. 把异步结果写入 Vue 响应式状态并触发布局、绘制。

对于 48 张卡片，正文前缀理论上可达到约 19.2 万字符；游客账号只有少量卡片时，同一问题很容易被设备性能掩盖。大账号进入列表后立即点击卡片，点击事件、详情渲染和编辑器模块初始化会排在这些主线程任务之后，因此表现为“详情骨架屏慢”，实际阻塞源头却在列表。

##### 2. 移动端后台同时预加载两套大型编辑器，制造随机长尾

历史策略会在 Android App 启动约 2 秒后同时导入 HTML 与 Markdown 两套编辑器，笔记库还会在列表加载后约 2.5 秒再次预热候选编辑器。修复时生产构建中的 TinyMCE 运行时约 470KB gzip，CodeMirror Markdown 运行时约 206KB gzip；下载完成后仍需在 WebView 主线程解压、解析和执行。

用户恰好在这些定时器触发时点击卡片，编辑器预加载就会与列表渲染、图片请求和真实导航争抢网络及主线程。这解释了耗时为何不是稳定增加，而是会随机从几百毫秒跳到 3 秒甚至 10 秒以上。

##### 3. “预加载”没有区分真正需要的资源和加载时机

移动端首次打开一篇笔记只需要一种编辑器。提前同时加载两种运行时，既浪费流量与内存，也把非关键任务放到了首屏和首次点击附近。预加载只有在页面已经稳定、设备确实空闲且资源很可能马上使用时才有价值；定时触发不等于空闲调度。

#### 修复方式

##### 列表协议改为服务端轻量预览

- 分页请求显式携带 `previewVersion: 2`。
- 服务端仍只读取最多 4000 字符的有界正文前缀，但在服务端一次生成最长约 300 字符的纯文本摘要、首图前后文字、首图位置和可信缩略图地址。
- v2 响应生成预览字段后删除 `content`，移动端卡片只整理字符串，不再逐卡执行 Markdown、DOMPurify 和 DOM 遍历。
- 未声明 v2 的旧客户端继续收到原 `content`，保证前后端滚动发布期间兼容；不能直接改变旧协议含义。

##### 移动端改为按用户意图加载

- App 启动和笔记库列表定时器不再后台导入两套编辑器。
- 笔记库稳定后只预热轻量的详情路由。
- 用户按下卡片时提前请求详情；点击成立后，详情数据与当前笔记对应的一套编辑器运行时并行加载。
- 编辑器在约 300ms 内就绪时直接交接；超过阈值则先展示已经取得的安全静态正文预览，运行时准备好后再替换成真实编辑器。
- 桌面端算力与并行能力更强，可以继续在首屏稳定后的空闲期预热两套运行时，但不得把桌面策略复制到移动端。

##### 图片预览保持低成本

- 卡片最多挂载一张 720px、质量 76 的 WebP 派生图，使用 `loading="lazy"`、`decoding="async"` 和 `fetchpriority="low"`。
- 图片按正文原顺序插入纯文本摘要流；图片失败时退回纯文本，不阻塞卡片或详情导航。
- 生产环境和 App 不允许回退原图；localhost 缺少生产缩略图目录时才允许使用经过校验的本站原图辅助开发。

#### 为什么全新安装后第一次打开也能很快

移除的是“无条件后台同时预加载两套编辑器”，不是取消所有提前工作。当前链路仍会预热详情路由、在手指按下时提前请求详情，并在点击后并行加载当前笔记真正需要的一套编辑器。列表不再占满主线程后，单个压缩运行时通常能在几百毫秒内完成；即使更慢，安全静态预览也会先让正文可见。

因此“全新安装、没有编辑器缓存仍然很快”并不矛盾，反而证明旧瓶颈主要是列表逐卡解析和错误预加载造成的主线程拥堵，而不是必须依靠编辑器缓存才能快速打开。

#### 防回归约束

1. **笔记库 v2 分页响应不得包含 `content`。** 卡片需要的新展示信息应增加有界、可审计的预览字段，不能为了方便把正文重新塞回列表。
2. **禁止在列表组件中对 N 条富文本逐项执行 Markdown 转换、HTML 净化或 DOM 构造。** 需要富文本派生信息时优先由服务端有界生成，或在专用 Worker 中处理；列表主线程只消费轻量结果。
3. **移动端禁止用启动定时器或列表定时器同时导入 HTML、Markdown 两套编辑器。** 只允许在明确卡片意图后加载当前类型；任何恢复全局预加载的方案必须先用冷缓存大账号证明收益。
4. **路由、详情数据和编辑器运行时应并行，而不是串行等待。** 慢运行时继续由安全静态预览兜底，不能重新让整页骨架屏一直等到编辑器完全可交互。
5. **性能验收必须覆盖大账号和冷缓存。** 只用游客账号、只打开已经访问过的笔记或只在桌面验收，无法发现这类回退。
6. **预加载要以主线程和网络竞争为成本核算。** “提前下载”不是天然优化；必须确认加载时机、命中概率、资源体积、设备类型以及是否与用户关键路径重叠。
7. **图片预览必须保持单图、压缩、懒加载和低优先级。** 不得因为恢复预览功能而把图片解码重新放到详情导航的关键路径。
8. **排查“接口快但页面慢”时必须分别测量请求完成、路由切换、正文首次可见和编辑器可交互。** 只看骨架屏时长会把主线程阻塞误判为数据库或网络问题。

### 云空间列表的弱反馈底色不要临时混入资源橙色（2026-08-13）

- **现象：** 云空间列表表头和普通文件行 hover 从接近白色变成明显的米橙色；不同页面缓存版本并存时，仅凭“线上看起来正常”还容易选错参照版本。
- **根因：** 被动层次背景直接通过 `color-mix()` 混入 `--resource-file-color`，之后再靠百分比反复微调。更反直觉的是，`f0426df8` 引入的移动渲染兼容层会把这两处语义弱底色包装成 `--ln-android-color-mix-file-soft-background`；命中 `html.light-note-mobile-rendering` 时，无论原权重是 1.5% 还是 3%，都会落到固定的 `rgba(255, 138, 0, 0.1)`，因此表头和 hover 同时被放大为明显的 10% 橙色。渲染配置按有效视口宽度触发，打开 DevTools 导致视口变窄也可能复现，并不代表 PWA 一定缓存了旧版本。
- **约束：** 表头和普通行 hover 分别使用 `--cloud-file-list-header-bg`、`--cloud-file-list-row-hover-bg`；亮色主题基准为 `#fffefc` 与 `#fffcf8`。批量选中态仍保留实色边标与更明显的橙色背景，不得与普通 hover 合并。
- **验收：** 以浏览器最终计算样式为准：亮色表头 `rgb(255, 254, 252)`、静止文件行 `rgb(255, 255, 255)`、hover 过渡结束后 `rgb(255, 252, 248)`；分别用桌面宽视口和 `?renderProfile=mobile` 验收，两套结果必须一致。同时检查暗色主题变量存在，不能为匹配亮色截图硬编码白底。

### Worker 任务诊断不能用 API 请求日志代替（2026-08-13）

- **现象：** 待处理中心的文件预览异常点击“查看诊断”后跳到 API 日志，并按 `file_preview` 模糊搜索；列表只能看到预览接口请求，无法定位当前失败 Job、派生文件状态或 Worker 领取时间。
- **根因：** `file_preview_jobs` 是异步任务事实，`api_logs` 是 HTTP 请求事实，两者没有可依赖的任务 ID 关联。把模块关键词当作诊断深链，只能得到同模块的若干请求，不能证明与当前异常有关。
- **约束：** 待处理中心的诊断入口必须携带来源表中的稳定主键，并由来源模块提供最小只读诊断接口；不得用模块名、标题或用户关键字跳到另一类日志冒充精确诊断。诊断响应只返回状态、错误码、时间线和安全元数据，不暴露对象存储 Key、Worker 主机名等内部信息。
- **验收：** 文件预览 Job 点击后留在待处理中心弹出任务诊断，显示相同 Job ID、文件、错误码、队列/派生状态和时间线；前后端回归分别断言不再生成 API 日志 target URL、诊断接口只按 Job ID 查询。

### 虚拟列表只优化 DOM，不能掩盖慢 SQL 和过重列表协议（2026-08-13）

- **现象：** API 日志已经使用虚拟列表，首屏仍明显慢于操作日志；日志量增长后差距继续扩大。
- **根因：** 虚拟列表只减少浏览器挂载的行节点。旧接口在空关键词时仍为每行计算五个 `LIKE '%%'` 条件，首屏还用 `a.*` 读取 50 条 `longtext req`、逐条解析 JSON，并在列表查询结束后串行执行精确总数查询；这些成本都发生在 DOM 渲染之前。进一步实测还发现 `api_logs.del_flag/status_code` 是历史 `varchar` 字段，SQL 却用数字 `0` 和 `CAST(... AS UNSIGNED)` 比较，MySQL 因隐式类型转换放弃 `(del_flag, request_time, id)` 索引，对约 11 万行、231MB 表执行全表扫描和 filesort；默认列表单次耗时约 2～2.5 秒。
- **约束：** 高频大表的空筛选不得生成无意义模糊条件；列表协议只返回列上可见的轻字段，大字段必须按稳定 ID 懒加载；首屏中互不依赖的列表和计数应并行。历史字符串状态列必须按字符串比较，禁止用数字字面量或包列的 `CAST` 破坏索引；隐藏少量内部账号的默认总数使用“活动总数－内部账号活动数”的窄索引精确计数，不逐行关联用户表。性能分析必须分别记录接口 SQL、执行计划、响应体积/解析和 DOM 渲染，不能以“已经虚拟化”推断后端一定快。
- **验收：** 默认 API 日志列表 SQL 不含 `LIKE CONCAT`、`a.*`、`a.req`、数字型 `del_flag` 比较或 `CAST(status_code...)`，点击单条后才请求详情；`EXPLAIN` 命中 `idx_api_logs_admin_list` 且不出现 `Using filesort`。生产只读同数据复测默认列表约 20～30ms，精确总数约 30ms；回归测试同时覆盖内部账号计数相减、组合筛选仍参数化、请求体 JSON 正常解析和非 Root 拒绝读取。

### 操作响应的局部快照不能覆盖初始化响应携带的能力字段（2026-08-13）

- **现象：** 成长中心点击签到、补签、单项领取或一键领取后，“今日成长与下一步”等 V2 区块立即消失；退出成长页再进入后恢复。
- **根因：** `/growth/me` 返回的成长快照额外携带 `features.growthCenterV2`，而各写操作只返回纯成长数据。前端把操作响应整体赋给共享 `growth` 后丢失 `features`，生产环境又以该字段决定是否挂载 V2 区块，因此把“局部响应缺字段”误判成“功能关闭”。
- **约束：** 同一账号的写操作响应如果只是领域局部快照，合并进共享状态时必须保留已由权威初始化接口确认、且本响应不负责返回的能力字段；不得用对象整替换隐式清空 Feature Flag。账号切换仍须清空全部旧账号能力字段，不能跨账号继承。
- **验收：** 在启用成长中心 V2 的账号上依次执行签到、补签、每日阶段领取、成长任务领取和一键领取，确认“今日成长与下一步”、成长足迹和偏好卡均保持挂载并原位刷新；重新登录另一个账号时仍按新账号 `/growth/me` 的开关裁决。`useGrowth.test.ts` 必须覆盖操作响应缺少 `features` 时保留当前账号 V2 开关。

### 循环键盘导航必须同步高亮项与滚动视口（2026-08-13）

- **现象：** 资源选择器在第一项按上箭头时，内部状态已循环到最后一项，但结果容器仍停在顶部，用户看不到高亮项，容易误以为选中状态丢失。
- **根因：** 统一的 `activeIndex` 只负责高亮与确认选择，没有在键盘移动完成后把目标项带入列表可视区；普通相邻移动不易暴露，首尾循环时最明显。补充滚动后又暴露出两个关联问题：程序滚动让静止指针下方换成新条目，`mouseenter` 会抢回高亮；结果容器的 Grid 自动行可收缩到按钮最小高度，多行标题、路径和范围说明因此被裁切或与下一项重叠。
- **约束：** 带循环能力的键盘列表必须在键盘移动后让当前项进入最近可视边缘；只能滚动列表自身，不能使用会推动外层页面的裸 `scrollIntoView()`。程序滚动会让静止指针下方的 DOM 条目发生变化，可能触发 `mouseenter` 并覆盖键盘高亮，因此必须在真实 `mousemove` 时才让鼠标接管。结果 Grid 的自动行必须使用 `max-content` 并从顶部排列，让 BButton 按标题、路径和范围说明自然撑高。快速连按使用即时滚动，界面缩放统一通过 `utils/zoom.ts` 换算。
- **验收：** 在结果超过一屏时，分别从首项按上、末项按下，并连续跨越上下边界；高亮项始终可见，外层页面位置不变，鼠标静止时不会把高亮抢回指针下方条目，真实移动鼠标后仍可正常切换；普通资源、当前页面和目录范围的两至三行内容均完整位于各自高亮背景内且不重叠。`ResourcePickerPanel.navigation.test.ts` 覆盖首项向上循环及键鼠竞争，`zoom.test.ts` 覆盖上下边界与已可见时不滚动。

### 官网进入应用的首轮导航必须提供按钮内反馈（2026-08-13）

- **现象：** 每次发布后用户首次点击“进入我的轻笺”，浏览器需要下载新的应用分包，页面短时间没有变化；只有浏览器 Tab 显示转圈，用户容易以为按钮失效或页面卡住。
- **根因：** 官网入口直接调用 `router.push('/app')`，没有把异步导航状态反馈到 CTA；应用路由的动态模块加载和首轮解析都发生在按钮点击之后。
- **约束：** 进入应用期间保留 CTA 文案，只把右侧箭头替换为现有加载图标并禁用重复点击；状态以 `router.push()` 的真实 Promise 为边界，不使用固定定时器。导航失败必须恢复按钮并给出收口提示，不新增轮询、全局监听或重复预加载。
- **验收：** 模拟未完成的路由 Promise，按钮立即设置 `aria-busy`、右侧图标旋转且文本不变，重复点击只发起一次导航；Promise 完成或失败后状态恢复。发布后以禁用缓存首次进入验证，加载反馈持续到应用路由就绪。
