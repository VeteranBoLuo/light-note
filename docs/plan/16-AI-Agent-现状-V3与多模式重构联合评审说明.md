## 0. 阅读说明

这份文档刻意把以下三类内容分开，避免讨论时混为一谈：

1. **当前主干事实**：当前轻笺 Agent 已有的产品能力、执行链路和状态机制；
2. **已观察问题**：近期真实使用中出现过的问题。部分具体问题已经做过局部修复，但仍作为架构回归样本；
3. **候选改造**：独立工作树中的 Runtime V3，以及后续讨论出的分层上下文和模式切换设想。它们均不应被当成既定结论。

希望评审者不要只回答“换模型”“加 Prompt”“减少历史”或“拆几个模式”。请同时考虑：普通连续问答、轻笺私有数据查询、资源材料问答、写操作确认、产物生成、Root 管理能力、失败恢复、成本和渐进上线。

## 1. 执行摘要

轻笺 AI 助手不是单纯聊天机器人，而是一个同时承担以下职责的复合 Agent：

- 普通知识问答和连续对话；
- 轻笺产品帮助与知识库问答；
- 对笔记、书签、文件、待办、标签等私有数据进行查询、统计和总结；
- 读取用户显式选择的材料、上传文件、图片或网页；
- 创建或修改轻笺内容，并通过预览卡、确认卡和幂等协议安全执行；
- 为 Root 提供受权限约束的管理查询；
- 生成长笔记、重新生成和继续修改尚未确认的产物；
- 输出引用、证据、处理记录和流式终态。

目前最突出的问题不是某一个工具不存在，也不能简单归因于 DeepSeek 模型能力不足。更核心的矛盾是：**一个请求可能经过多套语义判断，原始对话历史同时被用于理解指代和提供事实，能力元数据不完整，模型还承担了本应由服务端完成的资源、时间和参数绑定。**

因此会出现以下不稳定现象：

- 同一种意图换一种说法，有时会调用正确工具，有时却回答“不支持”或根本没有可执行计划；
- 连续会话中，上轮“最近 7 天”会污染本轮“今天”，上轮笔记材料会污染本轮书签查询；
- 已经选中的书签仍要求用户重新粘贴 URL；
- 明明存在可唯一定位的待办，查询结果却缺少提醒字段，模型只能说无法确认；
- Root 查询数量时可能遗漏、误算或用不完整结果回答；
- 长笔记草稿可能为空、长度不达标、重新生成丢材料，或者确认卡过期后连草稿也无法继续；
- 没有真实材料或工具结果时仍显示“本轮按当前工作区检索”；
- 输出引用与 Markdown 边界处理不正确时，URL 后面的普通文字也会成为链接。

Runtime V3 的试验方向是把 Agent 改成“唯一 TurnSpec、声明式 Capability Manifest、精确路由、服务端参数绑定、结构化 ResultSet/ArtifactState、严格材料边界和可灰度运行”。这个方向有价值，但目前 V3 把原始历史完全清空，会损害普通连续问答与知识库追问，因此不能直接视为最终架构。

最近讨论出的进一步方向是：

- 保留完整会话用于展示、审计和恢复；
- 推理时使用“有限近期原话 + 精简对话状态 + 结构化资源/执行状态 + 按需重新读取的当前证据”；
- 不同阶段使用不同上下文，Planner 和工具执行不读取原始历史；
- 可增加“自动 / 问答 / 查资料 / 执行”主模式，由服务端作为能力硬约束；
- 笔记、书签、待办等只作为次级范围约束，不把系统拆成大量互相隔离的 Agent。

本轮希望其他评审者独立判断：哪些 V3 机制应该保留、哪些需要修改、模式切换是否值得做，以及如何在不破坏原有普通连续对话的前提下提高工具选择和执行可靠性。

## 2. 产品定位与当前能力边界

### 2.1 同一个助手需要覆盖的场景

| 场景 | 典型问题 | 是否需要工具 | 是否需要连续上下文 |
| --- | --- | --- | --- |
| 普通知识问答 | “帮我解释一下 RAG 和 Agent 的区别” | 通常不需要 | 需要 |
| 普通知识连续追问 | “那它和刚才说的方案相比呢？” | 通常不需要 | 强需要 |
| 轻笺产品帮助 | “轻笺怎么导出笔记？” | 产品知识库读取 | 需要 |
| 已选材料问答 | 选择一篇笔记后问“这篇主要讲什么？” | 读取所选资源 | 强需要 |
| 工作区查询 | “我今天新增了哪些笔记？” | 私有查询工具 | 可选 |
| 跨模块查询 | “总结最近 7 天新增的书签和笔记” | 多个只读工具 | 可选 |
| 引用结果追问 | “第二个书签的地址是什么？” | 复用结果引用并重新取字段 | 强需要 |
| 写操作 | “把今天 16 点提醒的待办标记完成” | 查询 + 写工具 + 二次确认 | 强需要 |
| 长文产物 | “根据今天全部笔记生成至少 2000 字的新笔记” | 查询 + 生成 + 确认创建 | 强需要 |
| 产物继续修改 | “改为今天”“再详细一些，至少 2500 字” | 复用材料与草稿状态 | 强需要 |
| 图片与文件 | “总结这个 PDF”“识别这张图” | 文件解析、OCR 或识图 | 需要材料状态 |
| 网页处理 | “分析这个书签的网页内容” | 书签字段绑定 + URL 读取 | 需要引用状态 |
| Root 管理问答 | “今天有多少新用户？” | Root 专用查询 | 可选但权限敏感 |

### 2.2 当前能力规模

2026-08-20 的完整审计基线显示：

- Agent 工具约 55 个；
- 语义能力约 69 项，其中已启用能力约 55 项；
- 写工具约 11 个；
- Root 专用工具约 15 个；
- 工具覆盖笔记、书签、文件、待办、标签、综合内容、网页、账户、成长与管理等领域；
- 当前 Agent 是 Planner → Tool → Final Reply 的有界多阶段链路，不是无限 ReAct 循环；
- DeepSeek 为主要 Provider，千问作为备用 Provider；
- 写操作已有 owner 校验、风险策略、确认令牌、幂等和结果未知保护，这些安全底座不应被新架构绕过。

上述数字会随主干演进，但足以说明：问题不只是“模型不会选三个工具”，而是在几十项能力、多个身份和多种状态之间建立稳定协议。

## 3. 当前主干 Agent 链路

### 3.1 简化链路

```text
前端最新消息
+ 可见对话历史
+ 已选资源 / 上传附件
+ 工作区或当前材料范围
        │
        ▼
Agent 主 Handler
        │
        ├─ 动作续答判断
        ├─ 待草稿追问判断
        ├─ 材料承接判断
        ├─ 目录分析判断
        ├─ 笔记草稿专用判断
        └─ 其他直接路由与输入澄清
        │
        ▼
Runtime V2 Intent Compiler
        │
        ▼
Capability Router
        │
        ▼
Execution Planner / Validator
        │
        ├─ 旧 Planner 或语义修复回退
        ├─ 读取补全与依赖轮
        └─ 工具执行
        │
        ▼
确认卡 / 交互卡 / 产物草稿 / Final Composer
        │
        ▼
引用、证据、范围披露、SSE 终态、云端消息持久化
```

### 3.2 当前状态来源

| 状态 | 当前用途 | 主要风险 |
| --- | --- | --- |
| 云端 Conversation / Message | UI 展示、会话恢复、版本、引用与证据 | 展示历史与推理历史职责没有完全分开 |
| 前端消息列表 | 构建请求历史、重新生成、界面显示 | 客户端“显示什么就发送什么”，服务端难以判断权威性 |
| Runtime Session | 最近轮次、上一工具、Source Set、交互和动作 | 原始文本状态与结构化状态混放，TTL 后语义丢失 |
| Source Set / GroundingScope | 显式材料与允许引用的事实范围 | workspace/general 模式下隔离强度不一致 |
| Confirmation / Interaction | 写操作确认、选择与幂等 | 安全生命周期容易与草稿生命周期错误耦合 |
| 草稿和生成状态 | 预览、重新生成、替换 | 某些专用分支各自维护，难以统一继承和失效规则 |

### 3.3 当前链路的结构性矛盾

同一轮请求可能由以下模块分别判断一次顶层意图：动作正则、直接路由、材料追问分类器、待草稿分类器、笔记任务分类器、目录分析分类器、Runtime V2 Compiler、旧 Planner 和修复轮。它们看到的上下文不同，输出 schema 也不同。

因此即使每个模型调用单独看来都“多数时候正确”，串联后仍可能出现：第一个阶段把请求判断成新任务，第二个阶段把它当成上轮续写，第三个阶段又沿用旧时间范围，最后 Composer 再从历史正文补出一个看似合理但不可靠的答案。

## 4. 已观察到的问题与代表性场景

以下问题来自真实使用和截图。部分具体实现已做过局部修复，但所有场景都应继续作为架构回归测试，不能因为某一句话目前能通过就视为根因已消失。

### 4.1 工具有时执行、有时不执行

| 用户表达 | 期望 | 曾观察到的实际结果 |
| --- | --- | --- |
| “修改待办……” | 识别为待办修改，必要时查询目标并返回确认卡 | 回答“当前 AI 暂不支持修改待办”，没有执行任何工具 |
| 同一能力换一种措辞 | 仍映射到同一 capability | “AI 没有返回可核验的语义计划”，整轮失败 |
| “我今天新增了哪些笔记？” | 查询今天笔记并返回真实列表 | 没有生成可核验计划，或者错误认为没有材料 |
| “总结最近 7 天笔记并生成新笔记” | 查询材料、生成草稿、返回确认卡 | 偶尔只回复“已替换”，或生成空白确认卡 |

这类问题说明目前工具选择仍过度依赖措辞、候选目录、模型输出格式和回退链，而不是稳定 capability 协议。

### 4.2 查询结果不完整或模型乱回答

- Root 账号询问“今天有多少新用户”，实际有 2 位，回答曾只给出 1 位；
- 查询同名待办时，工具返回大量“推广”记录，模型根据不完整字段声称没有今天 16 点提醒的记录；
- 查询笔记时，工具或 Planner 失败后，最终回答没有明确区分“确实为 0”和“本轮没有成功执行查询”；
- 某些回答使用了列表中的部分样本，却以“全部”“只有”这类确定语气输出。

这里既可能有工具分页、字段投影或参数问题，也可能是 Composer 越过工具事实边界做了推断。架构需要明确：**未成功获得权威结果时，模型不得编造确定答案。**

### 4.3 时间范围被上一轮污染

代表场景：

1. 用户先说“总结我最近 7 天的笔记，生成一篇新笔记”；
2. 下一轮明确说“改为只总结我今天的全部笔记”；
3. 系统仍生成“近 7 天笔记汇总”，或者查询失败；
4. 再次用相同或近似说法，有时成功、有时失败。

正确语义应该是：最新消息中的“今天”完整替换旧范围，而不是和“最近 7 天”合并。时间表达还必须绑定到正确字段：

- 笔记、书签通常绑定创建时间；
- 待办可能涉及计划日期、截止时间和提醒时间；
- “今天 16 点提醒的那个”应同时约束提醒时间与必要的计划日期，而不是只做标题文本搜索。

### 4.4 旧材料串入新主题

代表场景：

1. 上一轮同时查询了笔记与书签，并引用一篇名为“尺寸”的笔记；
2. 下一轮用户只要求“查看最近 7 天书签的详细链接”；
3. 回答的引用材料中仍自动带上“尺寸”笔记。

另一类表现是用户明确改为今天的笔记，系统却继续使用上一轮 7 天材料。根因不是简单“历史太长”，而是旧材料正文、旧 Source Set、旧工具结果和原始对话同时参与了当前事实判断。

正确规则应是：

- 新主题默认不继承旧事实材料；
- 明确指代“刚才那些”“继续基于上轮材料”时才继承兼容的结构化结果集；
- 书签查询只能自动继承书签结果，不应继承无关笔记；
- 继承时保存稳定资源引用，真正回答前重新读取当前字段或正文。

### 4.5 已选资源仍无法解析“这个”“刚才那个”

代表场景：用户已经显式选择“百度一下，你就知道”书签，然后说“分析这个地址”。系统先要求提供 URL；用户再说“就是这个书签”，系统仍要求书签名称或链接；后续即使说“总结网页内容”，仍要求粘贴链接。

正确行为不应依赖模型从标题猜 URL，而应该：

1. 当前消息携带已通过 owner 校验的书签资源 ID；
2. 服务端按 Manifest 声明读取该书签；
3. 从权威书签记录绑定 URL 字段；
4. 把 URL 传给网页读取工具；
5. 最终回答引用书签和网页读取结果。

相同机制也适用于笔记正文、文件对象、待办 ID 和标签 ID，不能为“百度书签”写特判。

### 4.6 待办的提醒时间无法用于定位

用户页面上只有一条“今天 16:00”提醒的“推广”待办，但 Agent 查询同名记录后表示工具结果没有具体提醒时间，无法确认哪一条。

这反映出完整闭环缺失：

- 用户语义里已经有高价值定位字段；
- Compiler 应将其编译为提醒时间槽；
- 查询工具 schema 必须支持该字段；
- 数据查询必须投影提醒时间、计划日期和清单进度；
- 结果集应保存待办稳定引用；
- 后续修改只绑定唯一结果，多个结果才澄清。

如果任何一层缺失，模型再聪明也无法可靠定位。

### 4.7 长笔记生成与确认生命周期不稳定

已观察到的表现包括：

- 明明今天新增了多篇、正文很长的笔记，确认卡却显示“约 6 字”；
- 正文预览一直“生成中”，没有继续完成；
- 用户明确要求至少 2000 字，确认卡实际只有约 963 字；
- 用户要求重新生成更详细内容，旧操作被判定“已过期或已使用”；
- 引用 chips 仍在，但系统提示“原材料已不可用”；
- 重新生成时偶尔变成 0 项材料或 Source Set 不可用；
- 一张确认卡生成后，用户修改范围或长度，旧卡和新卡的关系不清晰。

需要区分三个生命周期：

1. **Source Set**：材料引用是否仍有效；
2. **Artifact State**：草稿版本是否可继续修改、替换或查看；
3. **Confirmation State**：某次写入授权是否仍可执行。

确认令牌过期，不等于材料和草稿同时失效；新草稿生成后，旧确认应原子失效，但旧材料可以在归属和版本仍有效时继续使用。

### 4.8 UI 披露与真实执行不一致

“本轮按当前工作区检索”曾在没有真实引用材料或成功工具结果时仍然显示。该文案会让用户误以为系统已经完成检索。

应只根据服务端权威终态显示：

- 本轮确实执行了工作区查询；
- 本轮确实使用了当前选择材料；
- 本轮继续使用了上一轮结构化结果；
- 本轮没有调用工具，仅进行了普通问答。

请求意图、模型计划和实际执行结果不能共用同一个披露字段。

### 4.9 输出渲染与引用边界

曾出现 URL 后面的“标题为……”等普通文本一起被渲染成链接。它可能来自模型输出的 Markdown 边界，也可能来自引用注入或前端自动链接正则。

这个问题不应通过修改某个回答文本规避，而要对以下协议分别验收：

- Markdown 显式链接；
- 裸 URL；
- URL 后的中文标点；
- 引用标记 `[1]`；
- 引用组件插入前后的文本边界；
- SSE 分片恰好切在 URL 中间时的合并结果。

### 4.10 与 Agent 主架构无关但暴露发布门禁的问题

书签智能识别后保存曾出现 `crypto is not defined`。该问题属于运行时兼容与前端实现错误，后来已做针对修复；它不是语义路由问题。但它说明发布验证不能只测试“模型返回了书签信息”，还必须真实走完保存动作及目标浏览器运行时。

## 5. 根因判断：模型问题还是架构问题

结论是：**主要是架构问题，模型差异会放大或缩小问题，但不能从根本上解决。**

### 5.1 架构责任

- 同一轮存在多个顶层意图判断器；
- 原始历史同时承担指代、事实、材料和动作续答；
- 能力目录不完全，部分领域和操作仍靠工具名、正则或相似度推断；
- Planner 能看到并复制不应由模型决定的 ID、URL、owner 和时间参数；
- V2 失败后可能进入另一套 legacy 语义链；
- 产物、材料和确认状态没有统一状态机；
- 最终回答没有在所有模式下严格限定为本轮权威事实；
- 测试多为标准问法，缺少同义表达和多轮状态矩阵。

### 5.2 模型责任

- 结构化 JSON 偶尔格式错误或字段遗漏；
- 在工具候选过多时可能选错相邻能力；
- 会把旧上下文中的显眼范围继续沿用；
- 可能在事实不足时生成听起来合理的解释；
- 对“生成、总结、创建、重新生成”等复合语义的边界判断存在概率波动。

### 5.3 为什么单纯换模型不够

更强模型可以提高单次分类或规划成功率，但仍无法解决：

- 工具结果根本没有提醒时间字段；
- 已选书签 ID 没有被绑定成 URL；
- 两套 Planner 对同一轮给出不同结论；
- 旧确认卡与新草稿缺少原子替换关系；
- UI 根据请求意图而非执行终态展示检索披露。

正确方向应是让模型只处理语言理解与有限参数抽取，把身份、权限、资源、时间、状态和事实边界收回到服务端。

## 7. V3 当前最大的争议与缺口

### 7.1 `rawHistoryMessageCount = 0` 过于绝对

当前 V3 试验版在 `v3_enforce` 下直接把原始历史选为空数组。这个规则能防止旧回答和旧材料污染 Planner，但也会破坏以下正常能力：

- 普通知识问答中的“继续解释”“那和前一种有什么区别”；
- 产品知识库问答中的代词和省略；
- 已选材料问答中的观点追问，而不仅是资源 ID 追问；
- 用户对上一条回答提出反驳、改写、翻译或风格调整；
- 需要理解上一轮自然语言结论、但不需要调用工具的对话。

结构化资源引用只能回答“哪个对象”，不能完整表达“刚才讨论了什么观点”。所以“完全不传原始历史”不能作为最终统一规则。

### 7.2 Manifest 不完整会造成能力消失

精确路由的前提是 Manifest 完整、正确并与真实工具一一对应。任何遗漏都会从“模型偶尔选不到”变成“系统确定性地永远选不到”。

需要解决：

- 所有现有工具如何迁移；
- 跨领域能力如何声明；
- 一个 capability 是否可绑定多个工具；
- 工具升级如何做版本兼容；
- planned / forbidden / role-limited 能力如何对用户披露；
- Manifest 与工具注册表如何在 CI 中双向校验。

### 7.3 严格失败关闭可能增加无意义澄清

如果任何不确定都要求用户补充，Agent 会从“偶尔乱猜”变成“经常追问”。需要定义：

- 哪些槽可以用唯一结果确定性绑定；
- 哪些可以使用当前页面或显式选择作为弱/强上下文；
- 哪些歧义必须澄清；
- 多目标请求能否先完成确定部分并清楚披露未完成部分；
- 如何评估澄清率，而不是只评估安全性。

### 7.4 结构化状态有 TTL、恢复与多端一致性问题

当前 Session 主要依赖 Redis/内存并有时效。如果用户：

- 刷新页面；
- 多标签页打开同一会话；
- 隔天继续旧会话；
- Redis 重启；
- 从另一设备继续；

那么 ResultSet、ArtifactState 和 DiscourseState 如何恢复，必须有明确规则。不能一边把原始历史移除，一边又让唯一语义状态只存在短 TTL 缓存中。

### 7.5 Composer 的上下文策略尚未完整解决

即使 Planner 不看历史，普通回答和最终 Composer 仍需要：

- 理解最近的对话语义；
- 严禁用旧回答作为当前私有数据事实；
- 对工具结果做忠实表述；
- 区分模型常识、产品知识库事实和用户私有事实；
- 保留引用并避免错误 Markdown。

这需要“按阶段组装上下文”，而不是一个全局的 history on/off 开关。

### 7.6 当前前端模块选择不是完整的模式系统

V3 已有的模块选择只是本轮 capability 域限制，发送后恢复自动。它能减少笔记、书签、待办之间的候选冲突，但不能表达：

- 用户只想普通聊天，不允许访问工作区；
- 用户允许查询，但绝不允许写入；
- 用户明确进入执行任务，希望后续“是”“继续”保持当前任务；
- 深度分析只改变回答预算，不改变工具权限；
- 识图属于输入能力，而不是长期业务模块。

## 8. 必须同时保留的问答场景

后续方案不能只优化工具执行，还必须证明以下场景不退化。

### 8.1 普通连续对话

示例：

```text
用户：解释一下 RAG 和 Agent 的区别。
助手：……
用户：那轻笺现在更接近哪一种？
用户：把刚才的解释改得通俗一点。
```

要求：保留最近观点语义，不强制调用轻笺工具，不因为没有 ResultSet 就失忆。

### 8.2 产品知识库连续问答

```text
用户：轻笺怎么导出笔记？
用户：移动端也是这样吗？
用户：刚才说的第二种方式有什么限制？
```

要求：能使用产品知识库事实和有限对话历史，引用仍可核验。

### 8.3 显式材料连续问答

```text
用户：@某篇笔记，这篇主要讲什么？
用户：作者的核心论点可靠吗？
用户：把刚才的分析压缩成三点。
```

要求：资源 ID 和版本结构化保存；正文按需重取；最近回答的论证结构可被继续讨论。

### 8.4 工作区只读查询

```text
用户：我今天新增了哪些笔记？
用户：其中哪篇最长？
用户：只看有正文的。
```

要求：第一轮真实查询；后续使用可核验 ResultSet 或重新查询；不能把模型回答当数据库事实。

### 8.5 跨模块查询

```text
用户：总结最近 7 天新增的书签和笔记。
用户：只列书签链接。
```

要求：首轮允许跨域；第二轮明确缩小为书签后不得继续引用笔记。

### 8.6 查询后执行

```text
用户：找到今天 16 点提醒的“推广”待办。
用户：把它标记完成。
用户：是。
```

要求：查询得到唯一稳定 ID；写操作生成确认；“是”只能认领当前确认；重复确认不得重复写。

### 8.7 长笔记产物链

```text
用户：根据最近 7 天笔记生成一篇新笔记。
用户：改为只用今天的全部笔记，至少 2000 字。
用户：再详细一点，至少 2500 字，不要编造材料事实。
用户：确认创建。
```

要求：最新范围替换旧范围；材料、草稿、确认分离；长度硬门禁；旧确认失效；最终写入幂等。

### 8.8 普通回答转产物

```text
用户：我们刚才讨论的方案不错。
用户：把刚才讨论整理成一篇笔记。
```

要求：这不是简单资源 ResultSet，需要一个明确、可审计的 Dialogue Anchor；不能因为 V3 不保存原始历史而无法完成，也不能把整段长期会话无限注入。

### 8.9 图片、文件与网页

- 图片：显式上传或选择图片后识别，不应长期固定在“识图模式”；
- 文件：解析完成前应展示明确状态，解析失败不能伪装成空正文；
- 网页：书签 ID 应由服务端绑定 URL，网页抓取失败要区分地址无效、抓取失败和正文为空。

### 8.10 Root 管理场景

- Root 工具只在真实 Root 普通管理上下文开放；
- 代管、只读预览和普通用户上下文必须失败关闭；
- Root 工具数量较多，不能因为 Root 身份把全部能力无差别塞给模型；
- 计数和列表必须有分页完整性、时间字段和“全量/样本”披露。

## 9. 讨论后的上下文优化方向

当前更合理的方向不是“完整历史全部发送”，也不是“原始历史永远为 0”，而是四层上下文：

### 9.1 四层状态

1. **有限近期原话**
   - 仅用于理解自然语言承接、观点、语气和省略；
   - 按 token/字符预算保留最近若干轮；
   - 由服务端从权威会话消息构建，不直接信任客户端拼装；
   - 不直接作为私有数据事实。

2. **精简对话状态**
   - 当前主题、用户目标、上一能力、未解决问题、会话模式；
   - 可以保存短摘要，但必须标记为语义提示，不是事实证据；
   - 摘要需要版本、来源消息范围和更新规则。

3. **结构化资源与执行状态**
   - ResultSet、Source Set、ArtifactState、Confirmation、Interaction；
   - 只保存稳定 ID、类型、版本和状态，不长期复制正文；
   - 每次使用前重新做 owner、存在性和版本校验。

4. **当前权威证据**
   - 本轮工具新查询结果；
   - 本轮重新读取的资源字段或正文；
   - 产品知识库命中内容；
   - 用户本轮直接提供的文本、文件和图片。

### 9.2 不同阶段看到不同上下文

| 阶段 | 可以看到 | 不应该看到 |
| --- | --- | --- |
| Intent Compiler | 最新消息、少量近期对话、精简语义状态、可用引用类型、模式约束 | 旧私有正文、旧工具完整结果、owner 与权限自由字段 |
| Capability Router | TurnSpec、Manifest、角色和模式白名单 | 原始自然语言和历史正文 |
| Execution Planner | TurnSpec、候选 capability、服务端绑定上下文 | 无关历史、范围外工具、未校验资源 |
| Tool Runner | 已验证参数与身份 | 模型历史、其他工具私有结果 |
| Final Composer | 最新消息、必要近期语义、当前权威证据、输出契约 | 无关旧材料、未执行计划、失败工具的猜测结果 |
| Artifact Engine | 当前 Source Set、明确 Dialogue Anchor、最新草稿版本、输出约束 | 整段无限历史、已失效确认作为材料 |

### 9.3 事实规则

- 普通常识可以来自模型，但应避免伪装成轻笺实时数据；
- 轻笺产品事实来自知识库或受控静态说明；
- 用户私有事实必须来自本轮权威材料或成功工具结果；
- 上一轮助手正文只能帮助理解对话，不能证明“今天有 2 位新用户”；
- 精简摘要也不能升级为事实证据；
- 如果本轮查询失败，回答必须明确失败，不能根据旧回答补一个数字。

### 9.4 话题与继承规则

- 完整的新请求默认推进 `topicEpoch`；
- “继续、再详细一点、第二个、这个”属于候选承接；
- 最新消息出现明确新领域或新时间范围时，覆盖旧范围；
- 只有类型兼容且唯一的 ResultSet 可以自动承接；
- 多个候选集合时澄清，不默认求并集；
- 跨领域请求必须由本轮明确表达，不能因为历史中出现过某领域而自动扩大。

## 10. DeepSeek 式模式切换是否适合轻笺

### 10.1 为什么值得考虑

模式可以在模型调用前缩小能力集合，降低以下风险：

- 普通聊天误调用写工具；
- 只想查询却生成创建卡；
- Root 管理工具干扰普通个人数据问答；
- 笔记、书签、待办相邻能力竞争；
- 同一句话既可解释为讨论，也可解释为执行。

但模式只能解决“本轮允许做什么”，不能单独解决材料串线、时间继承、字段缺失、产物生命周期和最终回答事实边界。

### 10.2 不建议照搬 DeepSeek 的三个模式

DeepSeek 的“快速 / 专家 / 识图”主要区分回答质量或输入能力。轻笺目前的核心冲突是：普通对话、私有数据查询和写操作混在同一个 Agent 中。因此建议按行为边界划分。

### 10.3 候选主模式

| 主模式 | 主要职责 | 允许能力 | 硬约束 |
| --- | --- | --- | --- |
| 自动 | 默认自然语言体验 | 按 Compiler 判断问答、查询或执行 | 仍受权限、材料、确认和候选预算限制 |
| 问答 | 普通知识、产品知识库、已选材料连续问答 | 普通回答、产品知识库、显式材料读取 | 不自动搜索整个私有工作区，不允许写入 |
| 查资料 | 查询、统计、总结轻笺数据 | 只读工作区工具、资源读取和安全分析 | 写 capability 从候选集合中硬移除 |
| 执行 | 创建、修改、删除和需要落库的任务 | 必要前置读取 + 写 capability | 所有写入继续二次确认，模式不能绕过权限 |

主模式应是服务端 `CapabilityPolicy`，不能只是 Prompt 提示。前端只能提交受支持的模式 ID，服务端根据 Manifest 的 effect、domain、role 和 risk 生成候选能力。

### 10.4 次级模块范围

可保留以下次级范围：

```text
全部 / 笔记 / 书签 / 待办 / 文件 / 标签 / 账户成长 / 管理
```

它的职责只是进一步收窄领域。例如“查资料 + 待办”只开放待办读取能力。它不应成为大量独立 Agent，也不能阻止合法的显式跨模块请求。

建议的状态规则：

- 主模式由用户显式选择后，在当前会话保持可见；
- 新建会话恢复“自动”；
- 次级模块默认只影响当前一轮，发送后恢复“全部/自动”；
- 若未来支持“固定模块”，必须显式展示且可一键取消；
- 模式切换不自动清空普通对话语义，也不自动继承旧资源材料。

### 10.5 其他开关不应混入主模式

- **深度分析**：改变模型、推理预算、延迟或输出详细程度，不改变工具权限；
- **识图**：在用户选择图片或显式开启时提供视觉输入，不是会话长期业务模式；
- **外部搜索**：只有真正接入稳定外部搜索后才展示，并与轻笺工作区检索区分；
- **当前材料 / 工作区**：属于 Grounding 范围，不等同于问答/执行模式。

### 10.6 模式系统的风险

- 模式过多会把系统复杂度转嫁给用户；
- 用户忘记当前模式时可能觉得“明明支持却不执行”；
- 如果每个模式复制一套 Prompt、工具表和 Runner，会产生更严重的漂移；
- “执行模式”仍需理解操作相关追问，不能把所有普通语言都拒绝；
- 自动模式仍然需要可靠 Compiler，模式不是路由器的替代品；
- 模式不能授予 Root 权限或扩大 owner 范围。

## 11. 不建议采用的简单方案

### 11.1 强制每轮选择笔记、书签或待办

优点是候选少，但会破坏自然对话和跨模块请求，并不能解决历史污染或参数绑定。可作为可选范围，不应成为必选步骤。

### 11.2 只保留最近固定 N 条历史

能降低 Token，但最近一条同样可能包含错误事实；同时无法稳定表达“第二个结果”或跨设备恢复。应按层级和阶段裁剪，而不是只按条数。

### 11.3 完全移除历史

对工具执行安全，却直接破坏普通连续问答、观点讨论和对上一回答的改写。V3 当前的绝对规则需要修改。

### 11.4 继续补关键词、正则和截图特判

短期见效，但会继续制造互相冲突的语义权威。正则只能做安全传感器或确定性的格式识别，不能成为顶层意图系统。

### 11.5 为每个模式复制一个独立 Agent

会产生多份 Prompt、能力定义、状态和回退逻辑，长期更难保证一致。更合理的是一个统一 Runtime，通过 Manifest 派生不同 CapabilityPolicy。

### 11.6 只换更强模型

可以作为 A/B 变量，但不能替代服务端字段、权限、状态和事实协议。

## 12. 后续架构必须满足的硬约束

1. 不能为某句中文问题写固定回答或专用工具分支；
2. 能力、领域、读写效果、权限、依赖和参数槽必须来自统一 Manifest；
3. 普通连续问答和知识库连续问答不能因工具安全改造而失忆；
4. 私有数据事实只能来自当前权威证据；
5. 原始历史不得进入 Planner 或 Tool Runner；
6. 模型不得决定 owner、Root 权限、代管上下文或资源归属；
7. 模型不得自由复制资源 ID、URL、时间和确认令牌；
8. 资源字段应由服务端按稳定 ID 重新读取和绑定；
9. 最新消息中的明确范围优先于旧范围；
10. 写操作必须继续使用确认、幂等、原子认领和结果未知保护；
11. 产物、材料和确认必须是三个可独立恢复和失效的生命周期；
12. 模式只能缩小能力，不能授予额外权限；
13. UI 只展示实际执行事实，不展示尚未执行的模型计划；
14. 每个复合目标都必须有可见终态，不能静默遗漏；
15. 新架构必须支持 legacy 回退、shadow 对比和按账号灰度；
16. 日常测试优先确定性 fixture，只对受影响工具做少量真实 Provider 调用；
17. 扩大灰度前必须有一次获授权的完整真实门禁，但不能每次开发都重复消耗全部工具 Token；
18. 任何重构都应复用现有业务 Service、owner 校验和确认体系，不另开副作用通道。

## 13. 希望其他 AI 重点回答的问题

请评审者在提出方案时明确回答以下问题，而不是只给原则性建议。

### 13.1 统一语义架构

1. 是否认可“每轮唯一 TurnSpec + Manifest 精确路由”？
2. Compiler 应由单个模型完成，还是先做确定性的模式/领域路由再调用模型？
3. 如何处理复合目标、部分支持、依赖和失败终态？
4. Manifest 应以 capability 为中心还是以 tool 为中心？如何处理一对多和多对一？
5. 如何避免 Manifest 不完整导致已有工具确定性消失？

### 13.2 上下文与记忆

1. 普通连续问答应该保留多少近期原话，按轮数还是 token 预算？
2. 精简摘要应如何生成、更新、过期和审计？
3. 如何保证摘要只用于语义理解，不升级为私有事实？
4. ResultSet、Source Set、Dialogue Anchor 和 ArtifactState 应分别保存什么？
5. Redis TTL 后如何从数据库消息恢复必要状态？
6. 多端、多标签页和重新生成时如何保证状态一致？
7. 新主题、范围替换、同域追问和跨域切换如何确定性判断？

### 13.3 模式切换

1. 是否需要“自动 / 问答 / 查资料 / 执行”四种主模式？
2. 问答与查资料是否应该合并，还是分开更能降低误调用？
3. 主模式应按会话保持还是每轮恢复自动？
4. 笔记、书签、待办等次级范围应如何展示，是否默认单轮？
5. 模式与 Grounding 范围、深度分析、识图和外部搜索如何避免概念重叠？
6. 当用户在错误模式里提出合法请求时，应拒绝、提示切换，还是一键升级本轮？

### 13.4 工具、参数与事实

1. 哪些参数必须服务端绑定，哪些可以允许模型抽取？
2. 工具结果应如何形成稳定 ResultSet，并支持“第二个”“这个”？
3. 查询工具需要统一返回哪些最小字段，才能支持后续动作？
4. Composer 如何确保数字、列表和状态不超出工具结果？
5. 跨模块请求如何合并证据，同时允许下一轮缩小范围？
6. 网页、OCR、文件解析失败时如何区分不同失败终态？

### 13.5 产物与确认

1. 草稿正文应保存在哪里，生命周期多长？
2. 新草稿如何原子替换旧确认，同时保留可用材料？
3. 硬字数、结构、Markdown 和“不得编造材料事实”如何确定性校验？
4. 确认过期后用户说“继续修改”应该如何恢复？
5. 如何处理 Provider 已生成内容但写入结果未知的情况？

### 13.6 迁移与验证

1. V3 哪些代码应保留、修改或废弃？
2. 如何在不重写 55 个工具的情况下渐进迁移？
3. shadow 应记录哪些低敏、低基数指标？
4. 如何证明新版本没有让以前能执行的工具消失？
5. 哪些测试必须真实调用模型，哪些必须禁止调用模型？
6. 灰度失败时如何在不回滚数据库的情况下立即恢复 legacy？

## 14. 建议其他 AI 输出的方案格式

为了便于后续横向比较，希望每个评审方案至少包含：

1. **根因判断**：模型、Prompt、工具 schema、状态和执行协议分别占什么角色；
2. **目标架构图**：每一阶段输入、输出和唯一权威；
3. **上下文模型**：近期原话、摘要、ResultSet、Source Set、Dialogue Anchor、ArtifactState 的 schema 与生命周期；
4. **模式设计**：是否需要模式、模式数量、持久规则和服务端约束；
5. **工具协议**：Manifest、参数绑定、依赖、跨域和权限；
6. **普通问答兼容性**：如何保证非轻笺问答和知识库连续追问；
7. **产物与确认状态机**：创建、重写、替换、确认、过期、失败、结果未知；
8. **迁移路线**：如何从当前 V2/legacy 迁移，如何 shadow、灰度和回滚；
9. **测试矩阵**：确定性测试、少量真实模型测试和生产门禁；
10. **成本分析**：模型调用次数、上下文 Token、延迟、缓存和真实测试费用；
11. **风险清单**：可能导致已有工具退化或普通对话失忆的地方；
12. **对现有 V3 的判定**：逐项说明保留、修改、删除或延期。

请尽量给出可以落地的 schema、状态转换和验收条件，不要只给“增强 Prompt”“增加记忆”“使用多 Agent”等抽象口号。

## 15. 建议统一使用的评测指标

| 指标 | 含义 |
| --- | --- |
| Tool Recall | 应调用工具的请求中，实际调用正确工具的比例 |
| Tool Precision | 已调用工具中，与用户意图匹配的比例 |
| False Unsupported | 已支持能力被回答为“不支持”的比例 |
| False Execution | 普通讨论或只读问题误进入写操作的比例 |
| Temporal Binding Accuracy | 今天、7 天、提醒时间等绑定正确字段和值的比例 |
| Grounding Contamination | 回答引用无关旧材料或旧结果的比例 |
| Referential Resolution | “这个、第二个、刚才那个”正确定位的比例 |
| Grounded Factuality | 私有事实是否完全可由当前工具或材料验证 |
| Goal Completion Coverage | 复合请求中每个目标都有明确终态的比例 |
| Clarification Rate | 系统要求补充信息的比例，过高代表过度失败关闭 |
| Confirmation Integrity | 写操作是否始终确认、不可重放、旧卡正确失效 |
| Artifact Contract Pass | 字数、格式、结构和材料约束一次或修复后通过率 |
| Conversation Continuity | 普通问答和知识库追问保持语义连贯的比例 |
| Mode Violation | 模式之外能力被调用的比例，目标应为 0 |
| Legacy Fallback Count | enforce 链是否偷偷进入旧语义系统 |
| Provider Calls / Turn | 每轮模型调用数及修复轮数量 |
| Token / Latency / Cost | 每种场景的输入输出 Token、P95 延迟和费用 |

## 16. 最小回归场景集

其他方案至少应能解释并覆盖以下场景族，而不是只通过一条标准问法：

1. “最近 7 天笔记”→“改为今天”→“至少 2000 字”→“再详细到 2500 字”→确认；
2. “最近 7 天书签和笔记”→“只列书签链接”，不能残留笔记；
3. 选择书签→“分析这个地址”→“总结网页内容”，不重复索要 URL；
4. “今天 16 点提醒的推广待办”→唯一定位→修改→确认→重复确认；
5. 同一工具至少 5 种自然说法，包括省略、口语和同义词；
6. 普通知识问答连续 5 轮，不调用轻笺工具；
7. 产品知识库连续追问并保留可核验引用；
8. 已选笔记观点讨论→压缩总结→保存为笔记；
9. Root 今日新增用户计数，分页和时间边界正确；
10. 工具超时、空结果、Provider 格式错误、Redis 状态过期和 SSE 中断；
11. 新会话不继承旧资源，旧会话恢复后只恢复允许的语义状态；
12. 问答、查资料、执行三种约束下使用相同句子，行为符合模式；
13. URL、中文标点和引用标记渲染边界正确；
14. 无真实工具或材料时不显示“已检索/已使用材料”；
15. 任何写操作在确认前均不产生真实副作用。

日常开发应优先使用 fixture、mock Provider、schema 校验和状态机测试。只有修改 Compiler、路由、受影响工具或扩大灰度时，才运行最少量真实 Provider 用例；全工具真实矩阵保留为获授权的发布门禁，避免反复消耗高额 Token。

## 17. 当前尚未做出的决策

本说明文档不预设以下答案：

- 最终是否采用四种主模式，还是三种模式；
- 问答模式是否允许自动检索轻笺工作区；
- 主模式是否始终按会话保持；
- 近期原话保留几轮或多少 Token；
- 对话摘要由模型生成还是确定性抽取；
- ResultSet 和 DiscourseState 是否需要持久化到 MySQL；
- Runtime V3 是否继续沿用当前实现，还是只保留其中的 Manifest、TurnSpec 和状态协议；
- 是否需要不同 Provider 分别承担 Compiler、Planner 和 Composer；
- 何时删除 V2/legacy。

这些问题应在收到多个独立方案、完成横向比较和补充实验后再决定。

## 18. 期望的最终结果

理想的新 Agent 应同时满足：

- 用户仍然可以像普通 AI 一样自然连续对话；
- 需要轻笺数据时能稳定选择正确工具；
- 同一种意图换说法不会随机变成“不支持”；
- 上一轮语义可以被理解，但上一轮私有事实不会自动污染本轮；
- 已选择的资源可以通过 ID 重新读取所需字段，不让用户重复粘贴；
- 时间、权限、owner、资源 ID 和确认由服务端掌控；
- 查询、执行、材料、草稿和确认状态边界清晰；
- 模式能减少候选冲突，但不会把用户困在大量模块按钮中；
- 所有写操作可预览、可确认、幂等且有可靠终态；
- 回答中的数字、列表、引用和检索披露都可核验；
- 新架构可以按 Root/白名单 shadow 和 enforce，异常时快速回退；
- 自动化测试覆盖语义族和多轮状态，真实模型测试费用可控。

这份文档的目的不是证明 V3 正确，而是让后续评审建立在同一组事实、问题和约束上。收到其他 AI 的方案后，应先逐项检查它们是否覆盖上述场景，再决定如何重构轻笺 AI 助手。
