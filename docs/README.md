## 临时材料

- `docs/plan/`：本地方案、评审输入和原型。默认被 Git 忽略，不是当前实现或规范的事实源。
- `docs/done/`：本地历史交付材料。默认被 Git 忽略，不进入开发必读。
- `docs/fix/`：本地排障草稿。默认被 Git 忽略，结论稳定后只把满足门槛的约束合并到正式文档。
- 临时材料只有在用户明确引用时才读取。方案落地后，将仍有效的决策合并到上表中的正式文档；已纳入 Git 的旧方案稿应删除。
- 不在临时目录保存凭据、生产数据、用户正文或不可恢复的唯一资料。

商店提交文案和合规审计属于交付证据文档，可以保留精确披露、日期与逐项证据；这类内容仍不得复制通用开发规则或演变成实施流水。

## 写作规则

1. **先选唯一事实源。** 同一规则只在一个正式文档完整说明，其他位置只写一句边界并链接过去。
2. **只写当前有效内容。** 删除“先做了什么、后来如何、某次测试通过、待上线”等时间线；需要追溯时使用 Git 历史。
3. **只写重要内容。** 记录架构边界、不可替代的业务语义、安全/数据约束、跨端规则和验收门禁；不记录局部样式值、单次修复过程或显而易见的代码行为。
4. **让代码承载易漂移细节。** 路由全集、字段清单、环境变量全集、常量、价格和概率优先由源码、Schema、脚本或契约测试表达。文档说明入口、含义和变更规则。
5. **结论优先。** 先写最终约束，再补必要原因和验收；避免背景复述、方案会议纪要和大段“为什么没有选其他方案”。
6. **短而可执行。** 一个主题通常只需要“边界 / 约束 / 验收”。能合并到现有条目时不新增标题，能链接时不复制。
7. **明确状态。** 规划内容不得写成已实现；未完成工作只在确有产品或安全风险时保留，并明确权威跟踪位置。普通待办不进长期文档。
8. **保护敏感信息。** 禁止写密码、Token、Cookie、连接串、私有对象地址、用户内容和可识别个人的数据。

## `pitfalls.md` 专用门槛

只有同时满足以下条件才记录：

- 已确认真实根因，不是猜测；
- 影响数据、安全、性能、生产环境、跨端兼容或跨模块一致性；
- 仅靠通用开发规范和现有测试不容易避免再次发生；
- 能给出可执行的约束与验收方法。

稳定条目使用：

```markdown
### 简短标题

**约束：** 根因对应的长期规则。

**验收：** 最小自动测试或人工验证。
```

同一根因出现新表现时更新原条目。排障现象、误导线索、修复提交和上线状态在结论稳定后删除。

## 文档变更自检

- 文档职责是否正确，是否已有唯一事实源；
- 是否删掉了重复、过时、历史状态和实现流水；
- 代码、Schema、脚本或测试中的名称是否真实存在；
- 相对链接与标题锚点是否有效；
- 是否误写敏感信息或把本地临时材料纳入 Git；
- 是否仅因“顺手”改动了与当前任务无关的用户文档。
